## 一、快速开始

**所有设置都在 `config.json` 的 `plugins.ai_chat` 段**（和 `bupt_news` / `essential`
同一套 ConfigManager 机制）。首次加载时如果这个段不存在，插件会把**完整模板**写进去，
所以打开文件就能看到全部开关和当前生效值：

```jsonc
// config.json → plugins.ai_chat（由插件自动补齐，下面是最小可用改动）
{
  "enabled": true,                                   // 模板默认就是 true；false = 整个插件不响应
  "llm": {
    "base_url": "https://myai.bupt.edu.cn/llm-gw/v1",  // 任意 OpenAI 兼容端点
    "api_key": "sk-...",
    "model": "deepseek-v4-flash",
    "reasoning": { "dialect": "effort", "default": "off" }   // 思考强度，见第七节
  },
  // 群里每个人各自有当前会话，无需配置
  "compaction": { "context_limit": 16384 }
}
```

补齐规则（三条）：

1. **只补缺键，绝不覆盖已改的值** —— 升级插件新增配置项时老部署会被自动补上，
   用户改过的一个都不动；
2. **写进去的是「有效值」**（内置默认深合并用户配置的结果），
   所以文件里看到的就是真正生效的，不存在「文件写了 A、实际跑 B」；
3. **幂等** —— 没有缺键就不写盘。

> 这三条现在是**框架对所有插件的统一契约**（插件声明 `config_template()`，
> 框架在构造插件时补齐），见 [`docs/plugin-dev.md` §15.3.1](plugin-dev.md#1531-首次运行即初始化全部配置项config_template)。

手工改完文件后：`/aichat reload --confirm=true`（超级用户 · 仅私聊），
或直接 `/aichat config` 查看/补齐。

启用后：

1. **私聊**直接说话，**群聊**先 @机器人；
2. 长内容可以分几条发 —— 因为单条 QQ 消息有长度上限 —— 最后发一条 `//` 收尾，
   意思是「**这一大段提交上去**」；
3. 机器人把这些分段**按顺序拼成一整段**当成一次输入（不加 `(1/3)` 之类的序号：
   分段只是客户端的限制，对模型来说本来就是一段话），回答再按长度自动分段发送。

```
用户：帮我看看       ← 暂存
用户：这周六有没有   ← 暂存
用户：讲座//         ← 提交，三条拼成一次输入
机器人：……
```

> ⚠️ 不 @机器人 的群消息**完全不进上下文**（与 DSH 的「只有明确输入才算用户消息」一致），
> 避免把整群闲聊灌进模型。

## 二、服务范围（只服务绑定的群 / 私聊）

**只对 `config.json` 里列出的群和私聊提供服务，其余一律回绝。**
这一判断**与权限等级无关**：超级用户在未开通的群里同样用不了 ——
服务范围是运维决策，不是权限决策。

```jsonc
"binding": {
  "groups": [100000003, 100000002],   // 允许使用的群号
  "users": [10000001],                // 允许使用的 QQ 号（私聊）
  "empty_means": "deny",              // 名单为空时的语义：deny=谁都不用（默认） / allow=不限制
  "notify_denied": false,             // 默认不发任何回绝提示（见 2.2）
  "notify_cooldown": 300              // 若开了提示，同一目标多久内只提示一次
}
```

回绝文案会直接指出该往哪个名单里加，例如：

```
⛔ 本群（99999）没有开通 AI 对话服务。请联系管理员把它加到
   config.json → plugins.ai_chat.binding.groups。
```

* **群**：开通了就是**全群可用**（群里每人各有自己的会话，所以不需要按人授权）；
* **私聊**：按人开通（框架从不限制私聊，这里是唯一的闸门）；
* 两者互不影响：群开通不会自动开放私聊，反之亦然。

### 2.1 两道闸门：群这层框架已经拦过了

| 层级 | 管什么 | 行为 |
|------|--------|------|
| 框架 `_on_ws_event()` + `GroupBinding` | 顶层 `bound_groups` | 未绑群的群消息在进 EventBus **之前**就被整条丢弃 |
| 本插件 `binding` | 群 + **私聊** | 框架**从不限制私聊**（`GroupBinding` 的注释写得很明确），私聊白名单只能由插件管 |

所以：

* **群**：`binding.groups` 为空时**回落到框架的 `bound_groups`** —— 同一个事实不在
  两处维护。注意 `bound_groups` 空列表的语义是「监听所有群」，与白名单相反，
  因此只在它非空时借用；两边都空就按 `empty_means` 办。
* **私聊**：框架不管，插件的 `users` 是唯一闸门。

> 未绑定的群即使有人 @机器人，插件也会回一句回绝说明（受 `notify_cooldown` 限制）；
> 没 @ 则完全静默，不会被群里闲聊刷屏。

### 2.2 未开通的聊天完全静默

不在服务范围内的群/私聊，**一个字节都不回** —— 连「你没有开通」也不提示。
理由：服务范围是运维决策，不该在别人的群里凭空冒出一条机器人消息
（有人会以为是机器人坏了，或者反过来去点它）。

实现上这一点由 [2.1](#21-两道闸门群这层框架已经拦过了) 的两道闸门保证：框架层丢弃未绑定群的
群消息，插件层把 `binding.groups/users` 白名单外的私聊与插件自派发的消息静默丢弃。

> 排查时可以把 `binding.notify_denied` 显式设为 `true` 临时打开提示
> （配合 `notify_cooldown` 限频）。**默认值必须是「不发」**：早先代码写成
> `get("notify_denied", True)`，于是老配置/精简配置因为**缺这个键**而退回
> 「要提示」，静默失效。

### 2.3 受邀例外：被邀请的人能用那个会话（仅私聊）

会话所有者可以 `/aichat invite` 一个**不在白名单里**的人；对方 attach 后就能在
**私聊**里用这个会话。这是刻意的「按会话授权」：所有者对自己建的会话的可见性负责，
不必为了拉一个人进来说话就去改全局白名单。

三条边界：

| 边界 | 行为 |
|------|------|
| **只在私聊生效** | 群里**没有**这条例外，仍按 `binding.groups` 判 —— 群是公共场所，否则任何人都能在群里把人拉进来用，群这道闸就形同虚设 |
| **判据是当前焦点** | 只有此刻正在用那个被邀请的会话才放行；单纯在受邀名单上不构成任何权限 |
| **取消邀请立刻失效** | `/aichat uninvite` 会同时摘掉对方的焦点，他下一次说话就被挡 |

⚠️ 实现上有个**鸡生蛋**问题值得记：服务范围的受邀例外判的是「当前焦点」，
而焦点只能靠 `attach` 建立 —— 但命令守卫会先按服务范围拦一遍，于是被邀请的人
在私聊里发 `attach` **完全没有反应**（实测），例外永远走不到。
所以 `attach` / `detach` 对「受邀的未绑定用户」单独放行（`CLAIM_COMMANDS`）。
放行的只是这两个动作；**能不能 attach 某个会话**仍由 `_may_attach` 判
（所有者 / 创建者 / 受邀者），不存在越权。

### 2.4 管理范围的命令不受范围限制（否则死锁）

`/aichat add`、`/aichat del`、`/aichat targets`、`/aichat reload`
**永远可用**（仍受「超级用户 + 仅私聊」约束），不经过服务范围判定。
同理，`/help aichat` 对超级用户**始终可见** —— 部署还没开通时，正是最需要
看到「用 add 开通」的时刻；未开通时把整个命名空间藏起来等于把出路也藏了
（普通用户仍然看不到这个命名空间）。

原因很实际：`bind` 只能在私聊用，而 `users` 为空 + `empty_means: "deny"` 时私聊
本身就被挡住了 —— 若不豁免，**永远开不出第一条私聊**，回绝文案还叫用户
「联系管理员」，而管理员正是执行这条命令的人。

### 2.5 其余命令同样受范围限制

未开通的地址连 `/aichat *` 都用不了：命令会被**静默丢弃**，既不回绝、也不回显
任何命令内容（否则等于向未开通的群暴露功能清单，还会暴露机器人的存在）。

`/help` 也必须同口径 —— 否则命令用不了、清单却列着，用户只会以为机器人坏了。
插件通过 `CommandManager.add_visibility_filter()` 注册过滤器，框架的 `/help`
在**列表与详情两处**都会询问它：

```
未开通的群：/help            → 整块 /aichat 命名空间不出现
未开通的群：/help aichat     → 未知命令: /aichat
未授权私聊：/help aichat.new → 未知命令: /aichat.new
```

过滤器只作用于本命名空间，别的插件的命令（`/ping` 等）不受牵连。

> 这与「服务范围」（第二节的 `/aichat add` / `del` / `targets`）是两件事：
> **谁可以调用服务**写在 `config.json`（本节的 `binding`），
> **哪个会话服务哪个聊天**是运行状态，存在 `data/sessions/state.json`。

### 3.1 三个概念，别混

| 概念 | 含义 | 存在哪 |
|------|------|--------|
| **服务范围**（绑定） | 这个群/这个人**能不能用** AI 对话 | `config.json → plugins.ai_chat.binding` |
| **归属** | 会话是**谁建的**（某个人 / 某个群） | 会话记录（`state.json`） |
| **焦点** | **某个人**在**某个聊天里**当前用哪个会话 | `state.json` 的 `focus` 表 |

一句话：**绑定决定「有没有这项服务」，焦点决定「用哪个会话」**，
`/aichat add|del|targets` 只管前者，与具体会话无关。

### 3.2 群聊会话 / 私聊会话：两个空间互不相通

会话按归属分两类，**能在哪里用由类型决定**：

| 类型 | 怎么来 | 能在哪里用 |
|------|--------|-----------|
| **群聊会话**（归某个群） | 在**群里** `/aichat new <名称>` | **只能在那个群里** |
| **私聊会话**（归某个人） | 私聊里 `/aichat new <名称>` | **只能在私聊里** |

也就是说：群会话不能被谁带进一对一窗口，私聊会话也不能拿到群里用
（早先「一个会话群聊私聊都能用」的设定已推翻）。想两边都有内容，就各建一个。

**会话不会自动创建**：说话不会凭空产生会话，必须显式 `/aichat new`。
没有会话时机器人会直接告诉你下一步做什么（群里若已有会话，会列出可用的让你 attach）。

### 3.2.1 焦点：谁在哪个聊天里用哪个会话

焦点键是 `聊天地址@user:人`，所以同一个群里每个人**各自的焦点**是独立的
（可以指向同一个群会话，也可以各用各的）；同一个人在不同群、以及他的私聊，
也都是各自的焦点。

### 3.3 参与别人的会话：邀请 + 自助 attach

> **受邀者可以不在服务范围白名单里** —— 这是「按会话授权」，但**只在私聊里生效**。
> 详见 [2.3](#23-受邀例外被邀请的人能用那个会话仅私聊)。

会话默认只有**所有者**能用。要拉人一起用：

```
/aichat invite <会话> <QQ号>       所有者执行（群归属的会话由群主/管理员代管）
/aichat attach <会话>             被邀请的人**自己**执行，才算用上
/aichat guests [会话]              看受邀名单
/aichat uninvite <会话> <QQ号>     取消邀请（会同时摘掉对方基于它的焦点）
```

**邀请只是授权，不会替对方切换** —— 对方要自己 `attach`。受邀之后，
他能在**这个群**里用该群会话（类型限制仍然生效：群会话不能拿去私聊用）。

> 群会话（在群里 `/aichat new <名称>` 建的）也不等于「全群可用」：
> 群成员同样需要被邀请。这是「邀请」要解决的问题。

### 3.4 命令

```
/aichat new <名称> [--attach=true]                        新建（位置决定作用地）
/aichat list [--user=<QQ>]                               当前聊天包含的会话（见下）
/aichat attach <会话>                                     直接切换你的当前会话（可跨位置）
/aichat detach [会话]                                     取消你在此处的当前会话（丢弃暂存区）
/aichat current                                           当前会话 + 上下文用量条
/aichat invite|uninvite|guests                            邀请管理（所有者）
/aichat rename <会话> <新名称>                             仅所有者
/aichat role [会话] [角色设定]                              设定 AI 在本会话扮演的角色（见 3.7）
/aichat delete <会话> --yes=true                           仅所有者
/aichat compact [会话]                                     立即压缩
/aichat history [--limit=10]                              历史提问清单（只给问题摘要，不出图）
/aichat hget <编号>                                       把某一条历史问答出成图片（一次一条）
/aichat hget #<段号>                                      按段落编号（[#N]）查，问/答都认
```

> **`detach` 会丢弃暂存区**：暂存区里那几段没提交的输入（还没发结束符）在解除时
> **直接丢掉**，回执里告诉用户丢了几段（如「暂存区里 2 段未提交的内容已丢弃；已取消…」）。
> 早先的做法是「有暂存内容就拒绝解除」，但暂存区分段往往正是用户想撤掉的半句话，
> 拒绝反而把人卡在那儿。

> **`attach` 直接切换**：已有当前会话时不需要 `--force=true`，也不需要先 `/aichat detach`
> —— 切换本质是**覆盖焦点**，不丢任何东西。旧的 `--force` 挡板已删除（写了也不会报错，
> 未知参数按位置参数吞掉）。唯一的前置检查是 `_may_attach`（群/私聊归属、是否受邀），
> 与切换无关。
>
> 切换**不动暂存区**：里面有未提交的分段时照切，分段留在原地（暂存区按「聊天地址」存，
> 不跟会话走），回执会说明「暂存区里还有 N 段没提交的内容，它们会并入这个会话」——
> 想丢掉就先 `/aichat detach`。

结束符后面跟 `md`（`你好//md`）→ **Markdown 模式**：回答渲染成图片发出。
详见[第十二节](#十二markdown-模式)。

**`list` 只显示「当前聊天所包含的会话」**：

| 在哪儿执行 | 显示什么 |
|-----------|---------|
| 群里 | 本群的群聊会话 |
| 私聊 | 你自己的私聊会话（含受邀参与的） |

要看**全部**（所有群、所有人的）用超级用户的 `/aichat listall`（仅私聊）。
`list --user=<QQ>` 供超级用户查某个人名下的会话。

`<会话>` 可以是 **id**（`s0007`）或**名称**（大小写不敏感，先精确后唯一前缀匹配；
有歧义时会提示用 id）。

> **布尔参数要写 `--key=value`**：`/aichat delete s0001 --yes=true`。
> 位置传参位上的布尔值只能写 `true`/`false`。写错会收到框架统一的
> 「⚠️ 用法不正确：… + 该子命令的帮助页」（不再由插件自绘报错）。

**帮助统一走框架的 `/help`**，本插件不自绘帮助：

```
/help aichat          子命令清单（名称 + 权限/作用域 + 介绍；参数与用法在下一级）
/help aichat new      单命令详情（权限/作用域、用法、参数、默认值、键值写法；与 /help aichat.new 等价）
/help                 全部可用命令与命令组（子命令在第一级不展开，见 /help aichat）
```

好处是帮助与真实校验**同源**：参数改了帮助自动跟着变，不会像手写的用法行
那样漂移。删掉自绘帮助后，「不用命令也能对话 / 结束符是什么 / 只对开通范围开放 /
每人各有会话 + 受邀参与」这些**非命令**的事写在命令组描述里（`/help aichat` 首屏）。

### 3.5 同一会话 = 同一份上下文

**共享是按会话算的，不是按人算的。** 只要两个人在用同一个会话，他们就**完全共享**
同一份历史：

* 后来的 `attach` 者立刻能看到之前所有对话（包括别人的发言）；
* 自己说的话对方下一轮也看得到；
* 上下文跟着**会话**走；而会话只能在其对应类型的聊天里使用（见 [3.2](#32-群聊会话--私聊会话两个空间互不相通)）。

因为共用会话里会有多个人说话，模型必须分得清谁是谁，于是：

| 情形 | 正文前缀 | 系统提示 |
|------|---------|---------|
| 只自己用（独享） | 不加 | 不提共用 |
| 会话有受邀者 / 多人说过话 | `[谁说的 · 时间]` | 明确告知「上下文完全共享、不要假设都是同一个人」 |

> `/aichat attach` 到一个共用会话时会提示「上下文与参与者完全共享」——
> 免得有人以为只是「用自己的会话看别人的历史」。

### 3.6 谁能用哪个会话

| 关系 | 能否使用 |
|------|---------|
| 所有者本人 | ✅ |
| 在受邀名单里 | ✅（群里、自己私聊里都行） |
| 群里其他成员 | ❌ 需要所有者 `/aichat invite` |
| 超级用户 | ❌ **不豁免** —— 服务范围由 `binding` 决定，但「用别人的会话」仍受归属约束 |

管理动作（改名 / 邀请 / 删除）只有所有者能做的；群归属的会话由群主/管理员代管。

### 3.7 角色设定（`/aichat role`）——压缩时原样保留

给某个会话指定 AI 扮演的角色，设定**只对这个会话生效**：

```
/aichat role                                   查看当前角色
/aichat role 你是一只猫娘，说话要带喵           设定（当前会话）
/aichat role s0003 你是一位数学老师             指定会话 + 设定
/aichat role --clear=true                      清除，恢复默认人格
```

角色描述可以写很多行、可以带空格（参数是变参，剩余位置参数全归它）。
上限 2000 字 —— 它**每轮都随系统提示发出去**，写太长就是每轮白烧 token。

#### 为什么它不会被压缩

这是设计上的硬保证，不是「碰巧」：

| | 存放位置 | 是否参与压缩 |
|---|---|---|
| 角色设定 | 会话字段 → **每轮重建的系统提示** | ❌ 不参与 |
| 对话内容 | 消息历史（`sessions/*.jsonl`） | ✅ 到阈值就被摘要吸收 |

压缩器（`Compactor`）只处理**消息历史**：它取一段历史、渲染成文字、让模型写摘要、
再用摘要替换那一段。角色设定根本不在历史里 —— 它在系统提示里，而系统提示每轮
由 `build_system_prompt()` 重新拼出来（见 [4.3 系统提示每轮重建、不落盘](#43-系统提示每轮重建不落盘)）。
**两者不在一条路上，所以压缩永远碰不到角色文本。**

这样做还解决了「压缩后人格漂移」：角色不是靠摘要记住的，压缩多少次都一个字不变。

> 摘要请求里**会**把角色设定告诉压缩引擎（并要求「不要改写、不要摘要它」）。
> 原因：摘要写给「接手的那一位」看，若它不知道有这个角色，可能写出
> 「助手表示自己是 AI 助手」这类与角色冲突的内容。这只是**告知**，
> 角色本体仍然只存在于系统提示里。
> 回归基线：`test_ai_chat.py` 的 `test_role_command`（含「检查点里没有角色正文」
> 「压缩后角色一字未改」「压缩后角色仍进系统提示」三条）。

#### 权限

| 动作 | 谁能做 |
|------|-------|
| 查看 | 能参与该会话的人（所有者 / 受邀者 / 超管）—— 设定直接影响他们收到的回复，看不到就成了「行为怪但查不出原因」 |
| 设定 / 清除 | 所有者（群归属的会话由群主/管理员代管）或超级用户，与 `rename` 同一把尺子 |

#### 两个使用上的坑

- **位置参数有歧义**：「第一格」可能是会话名，也可能是角色设定的开头。判据是
  「第一格能不能解析成一个真会话」—— 能才算会话名，不能就整句当设定。
  `/aichat role 你是一只猫` 不会被当成「会话『你是一只猫』找不到」。
- **群会话的焦点在群里**：`/aichat role` 不带会话时用的是**你在此处的**当前会话，
  同一个人在私聊和群里是两套焦点。在私聊里对群会话设角色要显式写会话 id。
- **引号会被命令解析层吃掉**：参数按 `shlex` 分词（框架的口径，见[使用文档 §6.2.4](usage.md#624-引号与转义字符串参数)），
  全角引号 `「」『』“”` 会先归一成 ASCII 引号再当定界符。所以
  `/aichat role 说话要带「喵」` 存进去是 `说话要带喵`。要保留引号本身得转义：
  `/aichat role 说话要带\\"喵\\"`。这不是角色功能特有的行为，所有变参命令都一样。

## 四、DSH 式消息包装

### 4.1 结构化消息，而非字符串

历史里每条消息是 `{role, blocks[], metadata}`（见 `segments.py`），
`tool_calls` 与 `tool` 结果是**成对的 block**，不是拼进正文的文本 ——
这样压缩时才能安全地切分（见 [5.3](#53-切点必须落在配对安全的位置)）。

### 4.2 只有人类输入才加「谁说的」

与 DSH 一致：**「是不是用户在问」由来源（`metadata.origin`）判定，不由正文决定**。

| 来源 | 是否加 `[说话人 · 时间]` 前缀 |
|------|------------------------------|
| `user.private` / `user.group` | 群聊 + 会话里出现过多个人时加（`wrapping.speaker_prefix=auto`） |
| `system.compact`（压缩检查点） | **不加** |
| `tool`（工具结果） | **不加** |
| `assistant` | **不加** |

> 少这一条，模型会把「历史摘要」当成某个群成员刚说的话，或者把工具结果当成用户发言。
> `wrapping.speaker_prefix` 可设 `always` / `never` 强制开关。

### 4.3 系统提示每轮重建、不落盘

分节顺序照搬 DSH：**人格 → 运行上下文 → 能力清单**。前面稳定 → prompt cache 命中率高；
时间这类易变信息放中间偏后，一变不至于把后面全作废。

运行上下文包含：当前时间/星期/时区、场景（群聊/私聊 + 群号）、会话名与 id、
当前说话人、以及「回复会自动分段，不要自己写 `(1/3)`」。

默认人格里明确要求**纯文本排版**：QQ 不渲染 Markdown，`**加粗**`、`#` 标题、
`|表格|`、代码围栏都会原样显示成符号。分点用「- 」或「1. 」，强调直接说，
贴代码裸贴。想改掉就设 `wrapping.persona`（会整体覆盖默认人格）。

系统提示**不进历史**（历史里也没有 `system` 消息）—— 它是当前环境的投影，
塞进历史只会变成随历史一起被压缩的陈旧信息。

### 4.3.1 引用：用段落编号指代，沿引用链追溯

用户引用了某条消息时，把它作为 `[引用上文]` 附在这条输入后面。

**① 上文还在上下文里 → 只给 `[#N]` 编号，不重抄原文。**
每条**文本段落**（用户输入、模型的回答）在请求里前面都带 `[#N]`，N 是它在会话里的
`seq`（落盘、压缩后依然有效）。所以引用一段还在上下文里的内容时，附上的是
`[引用上文] 对方引用的是上文 [#37]（原文已在上下文中，这里不再重复）` ——
既省 token，也不会因为转抄走样。这段内容不在上下文里（被压缩吸收 / 超出保留条数 /
换过会话）才退回贴原文，行为与以前一致。

**② 沿引用链往上追溯。** 被引用的那条自己可能也是引用别人的（群聊接龙、以及
「用户引用机器人回答、而机器人回答里本来就带着上一轮的引用」）。只读一层，
模型看到的就是半截话。现在：

| 情况 | 怎么追 | 层数上限 |
|---|---|---|
| 每一环都在历史里 | 走**本地** `metadata.reply_to`，**不联网** | `_QUOTE_LABEL_MAX = 10` |
| 某环不在历史里 | 用 `get_msg` 贴原文（每层 1~5 秒节流） | `_QUOTE_CHAIN_MAX = 3` |

```
[引用上文] 对方引用的是上文 [#12]（原文已在上下文中，这里不再重复）。
[引用上文] 上面那条自己又引用了 [#7]（同样在上下文中）。
```

旧版的样子（纯文本展开）：


```
[引用上文] 对方引用的那条消息内容如下：
中间那层说
[引用上文] 上面那条消息自己又引用了：
底层的原话：闭馆三天
```

用 `seen` 挡住环 —— 自引用的消息不会让读取转不出来（QQ 里理论上不该出现，
真出现了也不能卡住）。

**③ 引用 AI 的回答（含图片）时找得回原文。** Markdown 模式的整篇回答是**一张图**，
函数图、公式图也都是图 —— 这些消息在 QQ 那边**没有文字**，`get_msg` 读回来只有
「一张图片」。可那段内容本来就是这个插件自己生成的，原文一字不差地躺在会话历史里。
有了段落编号之后这条更简单：**在上下文里就只给 `[#N]`**（不再贴一遍原文）；
不在上下文里（压缩吸收过）才退回贴原文。

做法：

| 环节 | 做什么 |
|------|--------|
| `_send` | 把每条消息的 `message_id` 收进 `_sent_ids[聊天地址]`（**按聊天地址分桶** —— 不同会话是并发的，一个全局列表会把两个人的 id 混在一起） |
| `_run_turn` | 回复发完后，调 `_remember_sent` 把「这些 id → 本轮那条 assistant 消息」写进索引 |
| `SentReplyIndex` | 落盘 `sent_replies.json`，只存 `(sid, seq)` **不存原文** —— 原文已经在会话 jsonl 里，存两份迟早不一致，而且图片回复动辄几千字 |
| `_own_original` | 引用时按 id 查出 `(sid, seq)`，从会话历史里取回原文 |
| `_reply_media` | 能取回原文时**不再**回绝，交给 `_quoted_suffix` 补正文 |

给模型的形态是：

```
[引用上文] 对方引用的那条消息内容如下：
（这是机器人自己发的图片，以下是它当时生成的原文）
标准椭圆 x²/25+y²/9=1，长半轴 5，短半轴 3。
```

> 别人的图**读不到内容**，但**不会因此丢掉用户的问题** —— 原来只要引文是图片就
> 整轮回绝（「暂不支持多模态：…把要问的内容用文字发给我」），用户明明写了个好问题
> （「这张图里是什么」）却被一起扔了，连模型都没见到。现在那句话降级成一句**提示**，
> 落在引文的位置上，正文照常提交：
>
> ```
> [引用上文] 对方引用的是一条图片（暂不支持多模态，读不到里面的内容）。
> 这张图里是什么？
> ```
>
> 索引里没有的（重启前发的、超出保留条数）同样按这个口径处理。

> ⚠️ **`seq` 必须落盘（踩过一次，而且是「重启后必坏」）**：`Message.to_dict()`
> 早先漏写了 `seq`，`from_dict()` 也就读不回来 —— 于是**从 jsonl 加载的每一条
> 消息 `seq` 都是 0**，`SessionStore.find(sid, seq)` 一个都对不上，
> `_own_original()` 永远返回 None。表现：机器人自己发的图片，引用回来
> 只有一句「读不到」，而原文明明躺在历史里。进程内刚发的消息（缓存在内存里、
> `seq` 还在）看似正常，所以是「偶尔灵、热重载一次就全坏」。
>
> 两处修：`to_dict()/from_dict()` 带上 `seq`；`SessionStore._backfill_seqs()`
> 给**老文件**（磁盘上还没有这个字段的）从后往前倒推 —— 历史是尾部保留的，
> 最后一条的 `seq` 就是 `session.message_count`，往前依次递减，遇到带 `seq` 的
> 新记录就把它当锚点。线上验证方式很直接：`sent_replies.json` 里的
> `(sid, seq)` 取回来的正文，与 QQ `get_msg` 拿到的消息内容逐字一致
> （回归见 `tests/test_ai_chat.py::test_reply_index_survives_reload`）。

### 4.3.2 段落编号 `[#N]`

投影给模型的每条**文本消息**前都加 `[#N]`（`compaction.DshWrapping.project`），
N = 该消息在会话里的 `seq`：

```
[#35] [张三] 图书馆国庆开吗？
[#36] 10月1日至3日闭馆…
```

三条规矩：

* **只给有正文的消息编号**：工具结果、以及「只发起工具调用」的 assistant 片段
  都不是「段落」—— 给它们编号会把编号用掉，还会在工具协议那段 `content` 里塞一串
  没人引用的前缀；
* **`seq` 为 0 就不编号**（老数据 / 还没落盘）。两条消息共用一个编号比没有编号更糟；
* **系统提示里必须讲这件事**（`build_system_prompt(numbering=...)`）：告诉模型
  「要指代上文的某一段就写 `[#N]`，不要重抄原文」。提示与投影读的是同一个开关
  （`WrappingConfig.number_paragraphs`），关掉编号时提示里的说明也一起消失 ——
  否则模型会指着一个不存在的编号说话。

编号**稳定**：它来自 `seq`，落盘、压缩之后都有效（压缩保留的尾部消息 `seq` 不变）。

### 4.4 多段发送

- **入方向**：用户在结束符前发的多条消息按顺序拼成一次输入，带 `(i/n)` 标记，
  让模型知道「这是一条被截断的长消息」而不是多个独立话题；
- **出方向**：回复超过 `reply.chunk_max_chars`（默认 1200）时按换行优先切分，
  逐条发送；一旦断线就停止后续分段（不刷一堆失败）。

分页是**纯切分，不截断**：切点优先落在换行，其次空格，都没有才硬切；
所有分段的拼接等于原回复全文，所以模型不需要自己写 `(1/3)`（系统提示里也这么交代了）。

### 4.5 引用消息（reply）当上文

用户引用某条消息再发问时，被引用的内容会被读出来拼在输入后面：

```
那到底开不开
[引用上文] 对方引用的那条消息内容如下：
鲍勃：原问题：图书馆国庆开吗？
```

- 通过 `get_msg` 读取被引用消息（`reply` 段里的 `id`）；
- 只取**文本**段，`at` 段转成 `@QQ`；带上发送者昵称/群名片，模型才知道这话是谁说的；
- 引用的是图片/语音/视频/文件/合并转发/卡片/表情 → 直接回绝
  「暂不支持多模态：你引用的是XX，我只能读文字内容」，**不调模型**（省 token 也省得它瞎编）；
  同一条消息图文混排、但有正文时，正文照用，另加一句「（其中含图片，未读取）」；
- 读不到（被撤回、超出保留范围、接口失败）不阻断整轮，只标注「（引用的那条消息读不到内容）」。

> ⚠️ **顺序陷阱（踩过一次）**：结束符必须在拼引用内容**之前**剥掉。
> 结束符只可能出现在用户自己敲的那部分；先拼后剥的话 `//` 会被引文挤到中间，
> 而 `_strip_terminator` 只认行尾 → 永远匹配不到 → 表现为「引用了消息之后，
> 怎么发都不提交」。现在 `_extract_text_async` 只返回用户自身文本
> （另附多媒体类型名），引用正文由 `_quoted_suffix()` 在剥完结束符后单独拼。

## 五、上下文压缩

### 5.1 何时触发

估算 token 压力超过 `context_limit × threshold_ratio`（默认 `16384 × 0.8`）时，
在**进模型之前**就压缩，不等上游报超长。

token 是**字符数 ÷ `chars_per_token`**（默认 1.6，中文为主的聊天经验值）——
不引第三方 tokenizer，零依赖、行为可预测；它只用来决定「什么时候压」，
不参与计费，偏保守即可。

### 5.2 压多少、留多少

| 配置 | 默认 | 含义 |
|------|------|------|
| `context_limit` | 16384 | 自主设定的上下文预算（估算 token） |
| `threshold_ratio` | 0.8 | 到预算的这个比例就压缩 |
| `retain_ratio` | 0.16 | 压缩后保留最近多少比例的**原文** |
| `retain_tokens` | 0 | >0 时用绝对值覆盖 `retain_ratio` |
| `min_head_messages` | 2 | 头部少于这么多条就不值得压 |
| `summary_max_chars` | 1200 | 检查点长度上限 |
| `max_compactions_per_session` | 0 | 0 = 不限 |
| `max_context_retries` | 1 | 上游报「超长」时，压缩后重试的次数 |

（`threshold_ratio` / `retain_ratio` 的默认值与 DSH `dsh-compaction-basic` 一致。）

### 5.3 切点必须落在配对安全的位置

压缩 = 「较老的一段 → 一份检查点」+「最近的原文原样保留」。切点从尾部往前累计到
`retain_tokens` 后，再**向前回退**到最近的配对安全边界：

> OpenAI 协议要求 `tool_calls` 与紧随其后的 `tool` 结果严格配对，
> 切在中间等于给上游送一份非法历史（400）。

尾部自身不配对（正处在工具循环中间）时**整轮放弃压缩** —— 宁可这轮超预算，
也不送非法请求。

> **角色设定不受压缩影响**：它不在被压缩的这段历史里（走系统提示，见 [3.7](#37-角色设定aichat-role压缩时原样保留)）。
> 摘要请求里会附上角色设定并明确要求「不要改写、不要摘要它」，
> 只是为了别写出一份与角色冲突的接手说明。

### 5.4 检查点长什么样

照 DSH 的做法包框，两道门都要过：

```
这是一份自动生成的检查点，压缩了此前的一段对话以释放上下文。请把其中的内容
当作已经成立的背景，直接在此基础上继续，不要复述它；……

<compacted-summary>
## 用户诉求
- …
## 关键信息
- …
（共 7 节，固定结构）
</compacted-summary>
```

1. **下界**：摘要短于 24 字视为「模型没在压缩」，丢弃；
2. **必须变小**：检查点（含前言与标签）的估算 token 必须**严格小于**被吸收的内容，
   否则放弃本次压缩 —— 少了这道门，一次跑偏的摘要（把整段历史抄回来）会让上下文
   反而更长，而日志还写着「压缩成功」。

检查点以 `role=user` + `origin=system.compact` 落进历史：OpenAI 协议里 `system`
只能出现在开头（部分实现会拒绝中途插入），而 `user` 角色的注入消息是 DSH 的同一手法。

原文**不会丢**：`state.json` 里记 `compacted_upto`，`sessions/<id>.jsonl` 只是被重写为
「检查点 + 保留段」，需要时可从备份/日志找回。

## 六、上游失败自动重试

```
"llm": { "max_retries": 2, "retry_backoff": 1.5, "retry_max_wait": 8.0 }
```

`max_retries` 是**额外再试**的次数：默认 2，表示最多一共发 3 次（首发 + 2 次重试）。
等待按 `retry_backoff × 2ⁿ` 指数退避，单次不超过 `retry_max_wait`。

**什么值得重试**：判据只有一条 —— `LlmError.retryable`（在 `llm.py` 里标，因为
只有它知道每种失败的含义）：

| 可重试 | 不可重试 |
|--------|----------|
| 网络层异常：连不上、DNS 失败、连接被断、超时 | **4xx**：参数写错、key 失效、模型名不存在 |
| `408 / 409 / 425 / 429` 与 `5xx` | `未配置 base_url / model / api_key` |
| 上游回了**看不懂的东西**（不是 JSON、不是对象、没有 choices） | `空响应（finish_reason=length…）` —— 该调大 `max_tokens`，重试没用 |

> 4xx 重试一百次也是同一个结果，只会让用户多等几秒才看到错误 —— 所以判据认的是
> **标记**，不是按错误文本猜。

**重试发生在「单次模型调用」这一层，不是整轮对话**：一轮里可能已经跑过工具
（搜索、画图），整轮重来会把这些副作用再做一遍；而失败几乎总是「这一次 HTTP 没成」，
重发这一次就够了，工具结果与历史原封不动。

> 另有一条**上下文超长**的重试（压缩后换整个请求体重来），那条路要改请求体，
> 所以重试助手遇到超长错误**直接抛出**，不掺和。

`retry_notice` 打开时，**第一次**重试会给用户发一句「上游暂时不通，正在自动重试」——
否则用户看到的是十几秒的沉默，只会以为机器人没反应（这正是之前反复被问到的现象：
用户等不到回复就再按一次结束符，然后撞上「暂存区是空的」）。重试用尽后照旧把
错误原因发给用户。

**实际表现**（回归用例 `test_llm_retry` 覆盖）：失败两次后成功 → 模型被调 3 次、
用户拿到正常回答；一直失败 → 调用次数正好 `1 + max_retries`，然后报错；
`max_retries=0` → 一次都不重试；`401` → 不重试、立刻报错。

### 6.1 超时失败要附带「能照做」的说明

重试用尽后，光甩一句 `LlmError: TimeoutError` 等于没说：用户不知道是网断了、
额度没了，还是自己的问题太难。`_failure_hint()` 按**是哪种超时**给不同的建议：

```
⚠️ AI 对话出错（E-4c19）：PluginTimeoutError: 超过单次调用总时长上限 270s（已生成 1200 字正文）
（超过单次 270 秒的上限（没有再重试：同样的输入再跑一遍还是同样的时间）；先把已经生成的部分发给你了。这类问题拆小一点问更快，也可以调大 ai_chat.llm.timeout）
```

```
⚠️ AI 对话出错（E-4c19）：PluginTimeoutError: 流式读取停滞 60s（上游不再吐数据，已生成 0 字正文）
（上游 60 秒没吐任何数据，已重试 2 次，像是它那边卡住了。再发一次通常就好；连续出现就把 ai_chat.llm.stall_timeout 调大）
```

> 文案由框架的 `ErrorReporter` 渲染（`napcat/errors.py`）：**群里会 @ 出错时提问的
> 那个人**，括号里是稳定错误编号 —— 用户报编号、`grep` 日志就能定位。
> 早先那句固定的 `error_prefix` 前缀已经退役（同一类失败在别处会以别的写法出现、
> 没有编号、也不 @ 人），现在全框架只有一套错误文案。

**为什么要单独写一版超时文案**：线上实测 `deepseek-v4-flash` 遇到「这段 C++ 会报什么
运行时错误」会**连想 200 秒以上**（流式观测：14 000 字思考链、正文 0 字；放开
`max_tokens` 到 16384 后网关自己 300 秒回 504）。而用户唯一能看到的就是
`TimeoutError` 四个字 —— 把「拆小问题 / 调大 timeout」写进提示，是他自己就能试的
第一步。判据是错误文本里是否含超时关键词，`401` 这类不沾边的失败**不会**被加上
这句（回归见 `test_llm_timeout_hint`）。

### 6.2 流式（默认开）：把「想得久」和「卡死」分开

**症状**：同一句「讲讲定积分，并列表分析定积分和不定分的差异」，有时 41 秒答完，
有时 3 分钟还没动静，用户重试三次全超时。

**根因**：非流式请求里，「模型正在想 100 秒」和「上游彻底卡死」长得**一模一样** ——
都是没有任何字节回来。于是只能定一个总超时一刀切：定小了（90s）把正常但慢的回答
砍掉，定大了（300s）真要卡死时又让用户白等。实测同一句话的耗时在 **78s～240s**
之间分布（思考链 1699～3670 字），90s 正好切在中间，成功率全看运气。

**改法**：请求改成 SSE 流式（`llm.stream`），判据随之换成两个：

| 判据 | 配置 | 语义 | 可重试 |
|---|---|---|---|
| **停滞** | `llm.stall_timeout`（默认 60s） | 这么久**没有新数据** → 判定卡死，掐断 | ✅ 是（多半是它那边抽了一下） |
| **总时长** | `llm.timeout`（默认 270s） | 单次调用的硬上限（防无限流） | ❌ 否（再试也是同样的时间） |

只要 token 还在流就一直等 —— 这正是流式带来的新能力。掐断时**已经生成的部分会
带在 `LlmError.partial` 里**，`_run_turn` 会把它发出去（前面加一句「以下是已经
生成的部分」），而不是让用户白等一场空。

实现上（`llm._chat_stream`）：

* 自己攒行缓冲解析 `data:` 行，**不用** `async for line in resp.content` ——
  aiohttp 的行迭代有 64KB 行长上限（`LineTooLong`），而工具调用的 `arguments`
  分片、长公式都可能超；半行、`event:`、心跳注释、`[DONE]` 都在 `SseBuffer` 里处理；
* 工具调用是**按 `index` 累加分片**（`arguments` 常常被切成好几片，实测第一片
  甚至只有 `""`），最后统一走 `_parse_arguments`；
* `stream_options.include_usage` 让上游在最后一个 chunk 里带上 `usage` ——
  否则流式拿不到 token 用量，`/aichat current` 与日志里的统计会突然变 0；
* 端点如果忽略 `stream`、直接回普通 JSON（Content-Type 不是 `event-stream`），
  就退回原来的 JSON 解析 —— 所以「开流式」不会因为端点不认就整条路废掉；
* `timeout` 同时作为 socket 层的硬上限（`timeout + 15`）兜底，防的是「判据逻辑
  写漏了 → 永久挂住」。

> 为什么之前是 90 秒：那时 `timeout` 是「掐断判据」。流式之后它降级成兜底，
> 所以默认提到 **270** —— 本部署的网关自己会在 300 秒回 504，留在它下面才能
> 在掐断时把半截正文交出来（而不是收到一页 HTML 错误）。
>
> 回归：`test_sse_parse`（纯解析）、`test_llm_stream_cutoff`（起一个本地 aiohttp
> 假上游，覆盖正常流 / 非 SSE 回退 / 停滞 / 总时长四种）、
> `test_partial_reply_on_cutoff`（半截真的发给用户）。

## 七、思考强度（reasoning effort）

推理模型的「想多久」是一个独立开关，且**每家端点的字段名都不一样**。本插件把它
拆成两层：**意图**（用户说想要多强）与**方言**（往 payload 塞哪个字段）。

### 7.1 配置

```jsonc
"llm": {
  "reasoning": {
    "dialect": "effort",     // effort | thinking | enable_thinking | none | raw
    "default": "off",        // 全局默认：off / minimal / low / medium / high / max / 4k / thinking:on
    "per_model": {           // 按模型名精确覆盖（换模型自动换档）
      "deepseek-v4-flash": "off",
      "o4-mini": "high"
    },
    "params": {},            // dialect=raw 时原样并入 payload
    "max_tokens_floor": 0,   // >0：开思考时把 max_tokens 抬到这个下界
    "compaction": "off"      // 压缩摘要单独一档（摘要要短，思考是浪费）
  }
}
```

> 旧的 `llm.reasoning_effort: "off"` 写法仍然兼容（相当于 `dialect=effort` 的 default）。

### 7.2 方言对照

| `dialect` | 生成的 payload 字段 | 适用 |
|-----------|--------------------|------|
| `effort`（默认） | `reasoning_effort: "<level>"` | OpenAI / DeepSeek / 通义 |
| `thinking` | `thinking: {"type": "enabled"}` | DeepSeek V3.2 风格 |
| `enable_thinking` | `enable_thinking: true` | Qwen / vLLM 部署 |
| `none` | 什么都不发 | 让端点用自己的默认值 |
| `raw` | `params` 原样并入 | 自建端点万能兜底 |

给错字段名的代价很不对称：多数端点直接 400，少数**静默忽略**（你以为关掉了思考，
其实还在烧 token 和延迟）。所以方言必须显式配置，不靠猜。

### 7.3 强度取值

| 写法 | 含义 |
|------|------|
| `off` / `inherit` / `auto` / `none` | **不干预**：不发任何思考参数，由端点决定 |
| `minimal` / `low` / `medium` / `high` / `max` | 指定级别（`on` = `medium`） |
| `4096` / `4k` / `1.5k` | **思考预算**（token） |
| `thinking:on` / `thinking:off` | 显式开关（在 `effort` 方言里会翻译成级别，不会被吞掉） |

受方言能力限制时会**降级而不是报错**，并在 `/aichat think` 里说明：

- `thinking` 方言只有开关，没有级别 → `high` / `low` 都渲染成 `enabled`；
- 预算在 `thinking` 方言下退化为「开」，在 `effort` 方言下附带 `thinking_budget`。

> ⚠️ `low` 在部分 DeepSeek 部署上会被**服务端忽略**（实测 reasoning 454 vs `none` 的 0）。
> 想真正省 token 用 `off`，别指望 `low`。

### 7.4 命令

```
/aichat think                      查看当前生效值 + 会发的 payload
/aichat think high                 只改当前会话
/aichat think 8k                   思考预算
/aichat think off                  退回不干预
/aichat think low --global_=true   改全局默认（写入 config.json）
/aichat maxtokens                  查看本会话生效的 max_tokens（全局/覆盖/思考下界后）
/aichat maxtokens 2048             只改当前会话（8k 简写亦可）
/aichat maxtokens off              清除会话覆盖，回到全局默认
/aichat maxtokens 8192 --session=<id|名字>   改指定会话（需管理权限）
/aichat timeout                    查看本会话生效的单次调用时长上限
/aichat timeout 600                只改当前会话（10m / 1.5h 亦可）
/aichat timeout off                清除会话覆盖，回到全局 llm.timeout
/aichat model                      顺带显示思考强度
```

优先级：**会话覆盖 → `per_model[模型]` → `default`**。默认只改当前会话，因为
「这件事值不值得深想」和具体会话绑在一起更合理。

### 7.5 max_tokens 下界保护

推理 token **计入 completion**（`deepseek-flash` 实测占 ~93%）。`max_tokens` 给小了
会拿到 `finish_reason=length` 且 **content 为空串** —— 用户只看到「机器人没反应」。
所以开思考时会自动抬高下界（默认 4096；预算模式给「预算 + 1024」余量），
`/aichat think` 会显示实际用的值。
### 7.5.1 上游「自己会思考」时的空响应（实测）

有些网关/模型**不管你是否传思考参数，都会先吐一段思考链**（`reasoning_content`），
而思考 token 与正文共用 `max_tokens`。这时 `llm.max_tokens=4096` 的典型表现是：

- 难题（数学 / 竞赛 / 长推导）把配额全花在思考上 → 上游结束流时**只有 reasoning、
  没有 content、也没有 `finish_reason`**；
- 插件抛 `空响应（finish_reason=无，思考链 N 字）`，用户收到
  `⚠️ AI 对话出错（E-xxxx）：…`，会话里**只留下没被回答的提问**；
- 简单问题（「1+1」）4096 也够 → 于是表现为「只有某个会话怎么问都不回」。

实测（BUPT 网关 `myai.bupt.edu.cn/llm-gw/v1` + `deepseek-v4-flash`，同一段 math 会话历史）：

| `max_tokens` | 结果 |
|---|---|
| 4096 | 37s 后「空响应（思考链 989 字）」，无回复 |
| 8192 | 思考更久 → 撞 `llm.timeout=120` 超时 |
| **16384 + `timeout=300`** | **正常回复（409 字，assistant 记录已落库）** |

处理：

- `llm.max_tokens` 提到 **≥ 16384**，`llm.timeout` 提到 **≥ 300**（思考久时 120s 不够）；
- ⚠️ `reasoning.default=off` 只是**不发思考参数**（`build_params()` 在 off 时返回空
  dict，所有方言一致），**不等于让模型不思考**；`reasoning.max_tokens_floor` 也只在
  **我们要了思考**时才生效（`min_max_tokens()` 在 off 时直接返回 base），这条路上兜不住；
- 空响应会带错误编号（`E-xxxx`），`/aichat model` 可临时改本次运行的 `max_tokens`，
  但持久化要改 `plugins.ai_chat.llm.max_tokens` 再 `/aichat reload`；
- 单个会话想单独放宽等待时间，用 `/aichat timeout 600`（见 7.6.1），
  不需要改 `config.json`。


### 7.6 会话级 max_tokens（`/aichat maxtokens`）

`llm.max_tokens` 是**全局默认**；但「这个会话要不要长回答」其实与会话绑定更合理
（和思考强度同一个理由）。所以会话可以有自己的 `max_tokens` 覆盖：

| 命令 | 作用 |
|------|------|
| `/aichat maxtokens` | 查看：全局默认 / 本会话覆盖 / 实际生效（含思考下界） |
| `/aichat maxtokens 2048` | 只改**当前会话**（`8k`、`1.5k` 简写都行） |
| `/aichat maxtokens off` | 清除会话覆盖，回到全局默认 |
| `/aichat maxtokens 8192 --session=<id\|名字>` | 改指定会话（会话所有者 / 群主管理员 / 超管） |

- 覆盖值存在会话的 `meta.max_tokens` 里，**随会话持久化**（重启不丢）；
- 生效优先级：**会话覆盖 → `llm.max_tokens`（含 `/aichat model --max_tokens` 的
  运行期改动）**，之后仍会过一遍 7.5 的思考下界抬升；
- 合法范围 64–200000；`off`/`0` 表示清除；
- 全局默认要持久化改，仍走 `plugins.ai_chat.llm.max_tokens`（或
  `/aichat model --max_tokens=N`，仅本次运行有效）。

### 7.6.1 会话级 timeout（`/aichat timeout`）

`llm.timeout` 是**单次调用的总时长上限**（「想 + 答」加起来）。推理模型在难题上
可能想几十秒到几分钟，而这个上限是全局的；所以会话可以自己覆盖：

| 命令 | 作用 |
|------|------|
| `/aichat timeout` | 查看：全局默认 / 本会话覆盖 / 实际生效（并解释 `stall_timeout`） |
| `/aichat timeout 600` | 只改**当前会话**（`10m`、`1.5h` 也能写） |
| `/aichat timeout off` | 清除会话覆盖，回到全局 `llm.timeout` |
| `/aichat timeout 600 --session=<id\|名字>` | 改指定会话（会话所有者 / 群主管理员 / 超管） |

- 值存在会话的 `meta.timeout` 里，**随会话持久化**；合法范围 10–3600 秒；
- 生效优先级：**会话覆盖 → `llm.timeout`**，通过 `LlmClient.chat(timeout=…)`
  传到流式循环的 deadline 和 socket 超时；
- ⚠️ **和 `stall_timeout` 不是一回事**：`timeout` 是「总共最多等多久」，
  `stall_timeout`（默认 60s）是「多久没有新数据就判卡死」。思考链一直在流时，
  停滞判据永远不触发，只有 `timeout` 兜底 —— 所以难题超时应该调这里，
  而不是调 `stall_timeout`（后者调大只会让真卡死时等更久）；
- 调大的代价：上游真的挂住时要等更久才报错。建议 300–600，够覆盖慢思考，
  又不至于让用户干等十几分钟。

### 7.7 压缩摘要单独一档

摘要要求「短、密、结构化」，思考链在这里纯属浪费，所以 `reasoning.compaction`
默认 `off`。但有些推理模型关掉思考后摘要质量明显下降，所以留了单独配置的余地：

```jsonc
"reasoning": { "default": "high", "compaction": "off" }
```

### 7.8 手工改了 config.json 怎么生效

`ConfigManager` 只在启动时读一次文件。自己改自己（`/aichat think --global_=true`
之类）会同时更新内存与文件；但**手工编辑文件**后需要：

```
/aichat reload --confirm=true       # 超级用户 · 仅私聊
```

1. **可见即可用，但执行前再校验一次**：模型看到的清单按调用者权限过滤，真正执行时

### 8.1 与其它插件彻底解耦

**本插件不认识任何兄弟插件**：不 import 它们、不按文件路径加载它们、不读它们的
数据文件，也不为它们预留配置项。反之亦然（`bupt_news` 里没有一行提到 `aichat`）。

这里曾经有过一段耦合：内置工具会去读 `plugins/bupt_news/data/notices.jsonl` 拿校内
通知，并借 `bupt_news.weather` 的客户端报天气。那段已经**整块删除**，理由是它违反了
插件边界 ——

* 读的是别的插件的**私有数据文件**，对方改一次落盘格式就静默失效；
* 按文件路径加载对方模块，是为了绕开「不能在函数里做相对 import」才写的补丁，
  本身就是两层框架约束互相打架的产物；
* 对方的插件没装 / 加载失败 / 改过名，本插件的工具表就出现半可用状态。

要接外部数据，走**配置驱动**的路子（下一步的 `tools.custom`），那是显式的、可见的、
不改代码的。想查校内通知就直接在 QQ 里用 [`/buptnews`](bupt-news.md#四命令)；要让 AI 也能查，就把它配成一个
自定义 HTTP 工具。

> 老部署的 `config.json` 里可能还留着 `notices` / `weather` 两段（当年模板写进去的）。
> 插件启动时会**自动删掉**并记一条日志，不需要人工清理 —— 留着它们只会让人以为
> 这个插件还在读别人的数据。

### 8.2 自定义 HTTP 工具

不改代码就能挂工具（`tools.custom`）：

```jsonc
{
  "name": "campus_bus",
  "description": "查询校车时刻表",
  "parameters": {"type": "object",
                 "properties": {"line": {"type": "string"}},
                 "required": ["line"]},
  "method": "GET",
  "url": "https://example.edu/bus?line={line}",
  "headers": {"X-Token": "..."},

`{参数名}` 会被替换且做百分号编码（模型给的参数不能借道注入查询串或请求头）；
只允许 http/https，强制超时。

## 十、历史对话

两条命令，都在**当前焦点会话**上工作，共用**同一套编号**（都走
`history.extract_exchanges()`，不是各算一套）：

```
/aichat history [--limit=10]   列出**提问**清单（纯文字，按条分页；问给模型写的摘要）
/aichat hget <n>               把第 n 对（完整问答）渲染成图片（**一次只取一条**）
```

> **`history` 不给 AI 的回答**（连预览也不给）：它是「我问过什么」的目录，每条固定两行
> ——`编号. 谁 时间` + `问：<摘要>`。回答动辄上千字、一条里还覆盖多个要点，塞进目录
> 只会把编号冲散；要看某条答了什么走 `hget <n>`（出图，可保存/转发）。

### 10.1 一对问答怎么切

落盘的历史是**一串**消息：用户输入 → 「模型决定调工具」→ 工具结果 → … → 最终回答。
用户想看的是「我问了什么 / 它答了什么」，所以归并规则单独放在 `history.py`：

1. **连续多条 `user.*` 算同一对**（一次输入可能分几段发），起点取这段的第一条；
2. 答案是这一对里**最后一个有正文的 assistant 消息** —— 工具循环中间那句
   「我先查一下」不是答案，取第一条会让用户看到半句话；
3. 工具调用与工具结果**只计数**，折成图里一行小字（`🔧 调用了 get_notice ×2`）；
4. **没有回答的对不占编号**（答到一半崩了 / 刚问还没答）—— `list` 与 `get` 都跳过，
   两边编号才一致。

编号**不是永久 id**：压缩会把老消息换成一段摘要，被吸收的问答就从编号里消失，
后面的整体前移。这是有意的 —— 压缩后正文已经不在历史里，渲染它只能靠摘要瞎编。
清单里会明确提示「历史压缩过」。

### 10.2 清单为什么是文字 + 摘要

`history` 输出**纯文字**并按 `reply.chunk_max_chars`（默认 1200）分页 ——
一屏能看十几条，翻起来不用点开图片；`hget` 才出图，因为它的用途是「把这一条
完整保存/转发」。分页切在**条与条之间**，一条记录（两行）不会被劈成两半。

清单里的「问」**不是原文引用，而是模型写的 20 字摘要**
（`history.summarize` / `summary_chars`）；**回答不出现**：

```
📜 s0003 111 · 共 2 对问答（显示第 1-2 对）
看某条的完整问答：/aichat hget <编号>（如 /aichat hget 2，一次一条，出图）
1. snnsnn 09-30 22:41
   问：询问如何新建会话
2. snnsnn 09-30 22:43
   问：查一下今天的通知
```

为什么不用原文开头几十字：目录的用途是「一眼看出这条聊的是什么」，而中文提问的
开头常常是「我想问一下关于图书馆国庆期间的那个」—— 截断了也看不出要点。摘要要调
模型生成，所以**清单会多一次模型调用**；这是刻意的产品取舍，不是疏漏。

配套的三条约束（缺一条就会变成一个烧钱或骗人的功能）：

| 约束 | 为什么 |
|------|--------|
| **只给要显示的那几条摘要** | 列 10 条就只算 10 条，`--limit` 小就不会因子大 |
| **按内容指纹落盘缓存**（`history_summaries.json`，上限 2000 条） | `history` 是翻页查看的命令；没缓存的话每看一遍都重新烧一遍 token |
| **失败/关掉都退到截断，并在清单里说明** | 悄悄给一份截断文本、让用户以为那是摘要，比明说「降级」更糟 |

`history.summarize=false` 时完全不调模型，直接显示截断。未配置 LLM 时走同一条
退路（并提示「下面的问是截断而非摘要」）。

> 摘要请求走**压缩那一档**思考强度（`llm.reasoning.compaction`，默认关）——
> 写 20 字目录不值得开思考链。这段「策略 → 覆盖文本」的分支从 `Compactor` 里
> 提成了 `reasoning.override_text()` 共用，避免两处各写一份、以后加一种 mode 漏改一处。

### 10.3 一张图长什么样

`hget <编号>` 一次只取**一条**记录 —— 给区间（`3-5`）会被明确拒绝并给出替代写法。
先发一行文字头，再发那张图：

```
┌──────────────────────────────────────┐
│ 会话：预热群会话            第 3 对 / 共 12 对 │
├──────────────────────────────────────┤
│ 张三  09-30 22:15                      │
│ ┌──────────────────────────────────┐ │
│ │ 图书馆国庆开吗？…（浅蓝气泡）        │ │
│ └──────────────────────────────────┘ │
│ AI                                    │
│ 10月1日至3日闭馆，10月4日起自习区…      │
│ 🔧 调用了 get_notice ×2                │
└──────────────────────────────────────┘
```

`hget` 先发一行**文字头**（会话名 · 第几对 · 共几对 · 问答的段落编号），再发图 ——
图片在聊天里是独立气泡，没有头用户不知道这是哪一段、也没法接着翻。

#### 沿引用追溯：把上文一起画进卡片

单看一对问答经常缺上下文（这一对是接着上文说的）。`hget` 会沿**引用**往回追：
`history.trace_chain()` 用**本地**线索（`metadata.reply_to` → 另一对的消息 id）
把链上的问答都找出来，渲染进卡片上方那块灰色「引用链」区（每对只取问答各 240 字，
要看全文就 `hget` 那一对的编号）。文字头会写成：

```
🖼 预热会话 · 第 2 对（共 2 对） · 段落 问 [#3] 答 [#4]
沿引用追溯：第 1 → 2 对（图上灰色的就是前 1 对）
```

追溯**不联网**（不像贴原文那样每层一次 `get_msg`），也挡住环与断链：
上文被压缩吸收过、或老消息没记 `reply_to`，链就到此为止 —— 「追溯不到」比
「编一段上文」诚实。

#### `hget #N`：按段落编号查

模型在回复里用 `[#N]` 指代上文，用户拿到那个编号应该能直接查：

```
/aichat hget 2      ← 按「问答编号」（/aichat history 里的编号）
/aichat hget #37    ← 按「段落编号」（消息的 seq，问或答都认）
```

#### 卡片正文走**同一套** Markdown 渲染器

问题/回答的正文一律交给 `markdown_to_html()`（+ `katex_head()` + 共用的
`markdown_body_css()`），**不再自己 `html.escape` 一把**。

> 早先就是自己转义的，后果是：同一段回答在聊天里是排好版的公式，在历史卡片里
> 却是一串 `$$\frac{x^2}{25}+\frac{y^2}{9}=1$$` 源码（用户报过）。
> 同一份内容两种样子，根因是「渲染 Markdown」这件事有两个 owner。

同时统一的三件事：

| 项 | 说明 |
|----|------|
| 元素样式 | `markdown_body_css()` 是**唯一** owner（标题/列表/代码/表格/公式）。它原先被抄了三份，改一处漏两处 |
| 段内换行 | `markdown_to_html` 把段内的单换行渲染成 `<br>`，**不折成空格** —— 聊天里模型敲的每一行都是有意换的行，转录必须跟原话一样（Markdown 标准把软换行视作空格，那是为「手写文档自动折行」设计的，这里没有那个前提） |
| 量高度 | 卡片也要 `document.fonts.ready` 之后才量：公式的字体是异步加载的，早量会把卡片底部截掉 |

> ⚠️ 卡片上的 `.q/.a` **不能**再加 `white-space: pre-wrap`。正文改由 Markdown
> 渲染之后，段落之间那个换行会被 pre-wrap **多渲染成一行**，整段变成双倍行距。
>
> 另外踩了一个自己造的坑：`markdown_body_css()` 是从 f-string 里抽出来的，
> 抽出来之后**不再是 f-string**，可里面的 `{{` `}}` 还留着 —— CSS 里出现 `{{`
> 是无效规则，整段样式（包括表格边框）静默失效。回归断言：`markdown_body_css()`
> 里不许出现 `{{`。

#### 裁切只归文字模式

「按墨迹收口」（裁掉右下留白）**只对文字模式的块图生效**：

| 出图方 | 裁不裁 | 为什么 |
|--------|--------|--------|
| 文字模式的块图（表格 / 公式 / 列表 / 代码） | **裁** | 它要插在文字**之间**，必须紧贴内容；不裁会在两行字中间夹一条几十像素的白边 |
| 文字模式的行内公式 | **裁** | 同上，它就在一行字的中间 |
| Markdown 模式（整篇回答） | **不裁** | 它出的是一整「页」，页边距是版面的一部分 |
| 问答卡 `hget` | **不裁** | 同上 |

> 原先 Markdown 模式也走同一条裁切逻辑 —— 右下留白按墨迹被切掉，于是**内容长短
> 一变、页边距就跟着变**（实测同一套样式，一篇 698×467、一篇满宽），看着就不像
> 一页文档。现在 `render_markdown` 明确 `crop=False`。

> ⚠️ 判据别用「右侧白边有多宽」去量问答卡：卡片整页有灰底
> （`body{background:#f4f5f7}`），按白边量恒为 0。卡片要看**宽度是否等于配置宽度**
> —— 裁过的图会变窄。
>
> 另外，量边距要用 `png.read_png`，**不能手写 PNG 解码**：Chrome 截图的 PNG
> 逐行带 filter（实测有 1/2/4），忽略那个字节解出来是垃圾、边距恒为 0，
> 而断言看着还像通过。

### 10.4 渲染用 Chromium，不用画图库

这台机器上**没有任何图像库**（`import PIL` → ModuleNotFoundError），但装了
Chromium + Noto Sans CJK SC。用无头浏览器截图等于把排版交给真正的排版引擎：
中文换行、标点挤压、长英文断词都不用自己写。

**两趟渲染**（别简化成一趟）：

1. `--dump-dom`：页面里的脚本把内容真实高度写进一个元素，正则取出来；
2. `--screenshot --window-size=W,H`：按量到的高度截图。

一趟做不到自适应高度 —— `--window-size` 就是最终图像尺寸，而页面里的
`window.resizeTo()` 在无头模式下**被忽略**（实测：请求 600×900 拿回 600×900，
底部一大片空白）。

配套的三道闸（Chromium 是外部进程，缺一个都会出事）：

| 闸 | 作用 |
|----|------|
| `asyncio.Semaphore(1)` | 同时只允许一个 Chromium —— 群里连发 hget 否则就是 fork 炸弹 |
| 单张超时（默认 20s） | 超时 kill 并回「渲染超时」，不是永久挂住 |
| `keep_files`（默认 40） | 图片目录按 mtime 只留最近 N 个，防止慢慢写满 SD 卡 |

临时 HTML 与 Chromium 的 profile 目录（一次几 MB）在渲染后**无论成败都清掉**。

**注入防护**：群友昵称与消息正文一律 `html.escape` 后才进模板。不转义就是一个
自己给自己开的注入 —— 注入 `<img src="file:///etc/passwd">` 会被 Chromium 读出来
画进图里发到群里。页面里也不出现任何外部 URL，截图不会去联网。

### 10.5 顺序：先渲染完，再发头

渲染失败时用户必须看到**一句错误**，而不是先收到「🖼 第 1 对」然后什么都不来 ——
一个没有下文的头比一句错误更让人困惑。所以流程是「全部渲染成功 → 发文字头 →
逐张发图」，任一环节失败都只回一条明确的错误。

## 十一、联网搜索

`web_search` / `fetch_page` 两个工具，让模型能回答「今天/最近」类问题。

### 11.1 为什么是两个工具

搜索摘要常常只有几十字，而「XX 什么时候」「怎么做」这类问题往往要读正文。
所以拆成「先搜 → 挑链接读正文」两步，token 花在模型自己判断有用的页面上。
这也是**一个提问、多段回答**的关键：不同来源各自成段，而不是把一堆摘要糊成一段
（工具指引里明确要求分段并标注来源）。

### 11.2 两条路：JSON API（推荐）与抓公开搜索页

**默认走 AnySearch**（`https://api.anysearch.com/v1/search`，**匿名即可用**）：
它是排序式的检索服务，结果干净、可引用，实测同一批查询 **0.5~2 秒**返回且直接命中
（「北京邮电大学 图书馆 国庆 开放时间」第一条就是北邮图书馆的开放安排）。

为什么默认不用抓页面：抓公开搜索页在有些网络里**根本走不通**。实测这台机器上
百度返回「安全验证」、搜狗要验证码、知乎 403、360 给空壳、Bing 返回一批**无关**
结果（对同一个查询返回 Bilibili 与北京市政府页面），而且抓页面要 **8~14 秒**
（含浏览器渲染兜底），AnySearch 只要 0.5~2 秒。

> 老部署（`api_url`/`api_key`/`api_tag` **三个键都空**）会在加载时**自动接入**
> AnySearch 并记一条日志；只要用户给其中任何一个填过东西就一个字都不动。
> 想显式走抓页面：把 `api_url` 留空（`""`）—— 这与「没配过」是两回事。

也支持换成别的 JSON API：

```jsonc
"search": {
  "api_url": "https://api.tavily.com/search",  // 或自建 SearxNG 的 /search
  "api_key": "tvly-xxxx",                      // SearxNG 一般不需要
  "api_method": "POST",                        // 或 GET
  "api_fields": {}                             // 可覆盖字段路径（见下）
}
```

配了就先走 API；没配或 API 失败才回落抓页面。响应解析兼容多家形状
（AnySearch `data.results[]` / Tavily / SearxNG / Bocha / 通用 `data[]`），
字段名按候选路径逐个试，也能用 `api_fields` 显式指定
`list_path` / `title_key` / `url_key` / `snippet_key`。

**垂直检索**用 `api_tag`（`<领域>.<子域>`，如 `academic.search`、`code.snippet`、
`finance.quote`）：AnySearch 提供 17 个领域，清单在 `search.ANYSEARCH_DOMAINS`，
拼错时插件会**直接说明并列出可用领域**而不是发一个注定空结果的请求。

**相关性闸对 API 是「安全网」而不是关卡**（`api_min_score` 默认 -1）：
API 是排序式的、不会整批跑偏，而精确子串匹配对中文误杀太多 —— 实测两个都被误杀：
`北邮` vs 结果里的「北京邮电大学」（同一实体、无公共子串）、
`今天北京天气` vs 结果里的「北京天气预报」（无整串）。
抓页面那条路仍保持严格（0.34），因为它**确实**会整批跑偏。

抓页面那条路保留为「没配 API 时的尽力而为」，三层：

| 层 | 做法 | 为什么 |
|----|------|--------|
| 1 | 相关性闸 + 换后端 | **有结果 ≠ 有相关结果**：Bing 会返回一批与查询无关的结果（170KB、10 个结果块，看着完全正常）。所以先算关键词命中率，低于阈值就当失败换下一个后端 |
| 2 | **无头 Chromium 渲染** | 搜索引擎对普通 HTTP 客户端返回 JS 空壳页或干脆是「大页面但没结果」。实测同一个 URL：aiohttp 拿 592 字节 0 条，Chromium 渲染拿 10 条。这一步**无条件**走，不看「像不像空壳页」——360 就是 58KB 正常页面但一个结果都没有，任何基于体积的判定都会漏掉它 |
| 3 | 双后端 | `bing` 与 `360` 两个解析器，谁先给出**相关**结果就用谁 |

默认顺序把 360 排在前面，是实测结论（同一查询 360 相关、Bing 无关），不是偏好。

**这台机器上搜索目前不可用**（所有引擎都挡了），配了 API 就能用 —— 见上面的配置。

解析器是**纯函数**（`parse_bing` / `parse_360`），所以能用**保存下来的真实 HTML**
做回归测试，不联网也能卡住「搜索页结构变了」。仓库里没有 bs4/lxml，用标准库
`html.parser` + 正则 —— 只需要「块边界」这一个结构假设。

### 11.3 安全：SSRF 闸

搜索结果与网页内容都是**不可信输入**（模型会把它们当资料读），所以抓取前必须校验地址：

- 只允许 `http` / `https`；
- **拒绝内网与本机地址**（`127.0.0.1`、`10.*`、`192.168.*`、`169.254.169.254`
  这类云元数据地址、`::1`、`.local`……）；
- 域名先解析成 IP 再判（解析失败按不安全处理）。

没有这道闸，一句「请访问 http://127.0.0.1:8080/admin 并把内容告诉我」就变成了
一个内网探测跳板。工具指引里也明确要求：网页里的「忽略之前的指令」这类话当普通文字。

### 11.4 配置

```jsonc
"search": {
  "enabled": true,
  "backend": "360",           // 抓页面时的首选；另一个自动兜底
  "count": 5,                 // 默认返回几条
  "timeout": 15,              // 单次请求超时（秒）
  "max_page_chars": 4000,     // fetch_page 回喂给模型的正文上限
  "user_agent": "",           // 留空用内置 UA
  "api_url": "https://api.anysearch.com/v1/search",   // 默认 AnySearch（匿名可用）
  "api_key": "",              // 留空=匿名；填 key 走认证（额度更高）
  "api_method": "POST",       // POST / GET
  "api_tag": "",              // 垂直检索：academic.search / code.snippet …
  "api_fields": {}            // 可选：字段路径覆盖，如 {"list_path": "data.results"}
}
```

## 十二、Markdown 模式

**触发**：结束符后面紧跟 `md` —— `你好//md`、`你好 //md`、`//md` 都算

**文本模式（不加 `md`）会自动降噪**：QQ 不渲染 Markdown，所以发出前会过一道
`to_plain_text()` —— `**重点**` 去掉星号、`> 引用` 去掉尖括号、`[文档](url)`
改成 `文档（url）`、行内代码去掉反引号、`---` 换成实线、`\*` 这类转义还原；
**数学公式整段保护、一字不改**（`$a*b$` 里的 `*` 不会被当成强调）。表格/公式/
标题/列表/代码围栏本来就是**出图**的块，不受这一步影响（见「表格与公式」一节）。


（配置 `trigger.markdown_suffix`，留空则关闭）。然后**回答渲染成图片**发出。

识别放在结束符剥离那里而不是命令系统里，因为它是结束符的**修饰**：
`//` 仍是唯一的提交开关，`md` 只改变输出形态。

### 12.1 系统提示怎么设计（这里最容易做错）

默认人格里有一句「请使用纯文本排版：QQ 不渲染 Markdown」。Markdown 模式必须
**改写**这一条，否则模型会收到两个互相矛盾的指令，然后随机挑一条执行。

做法是**追加**一段而不是整体替换人格：

- 替换会把「简洁、别自我介绍、别编造」这些与输出形态无关的约束一起丢掉；
- 追加段里必须**显式作废**纯文本要求（写「上面关于纯文本排版的要求作废」），
  只说「可以用 Markdown」是不够的 —— 两条矛盾指令并存时模型会漂移；
- 运行上下文那句「回复会分成多条 QQ 消息」在 Markdown 模式下也要换成
  「会渲染成一张图片」，否则系统提示自己前后矛盾。

同时，工具指引按**本轮能力**拼：没开搜索就不讲搜索，非 Markdown 模式就不讲
Markdown —— 提示里讲不存在的工具会让模型空调用一轮。

### 12.2 渲染：自己写 Markdown 子集转换器

仓库里没有任何 Markdown 库，所以 `markdown.py` 实现了一个**受支持子集**
（标题 / 粗斜体 / 行内与围栏代码 / 有序无序列表 / 引用 / 表格 / 分隔线 / 链接），
未支持的语法原样显示，不报错也不吞内容。

必须自己做对的是**转义**：模型输出与它抓回的网页内容都会进模板，不转义就是
自己给自己开的注入（注入 `<img src=file:///etc/passwd>` 会被 Chromium 读出来
画进图里发到群里）。处理顺序不能错：

1. 先摘出代码（围栏块 + 行内）占位 —— 晚了的话代码里的 `**` 会被当成粗体；
2. 再转义所有文本；
3. 最后拼标签。

出图复用问答卡那套「两趟渲染（量高度 → 按高度截图）+ 并发闸 + 超时 + 目录有界」。

### 12.3 文本模式下的表格与公式：挑出来出图，插回消息体

默认人格要求纯文本排版，但模型**确实会**用 Markdown 表格和 LaTeX（真实会话里
就有）。与其假装它不会，不如把这些块挑出来单独出图 —— 否则用户收到的是
一堆竖线和反斜杠。

`markdown.split_rich_segments()` 把回答切成
`文本 / 表格 / 公式 / 文本…`（**保序**），`_send_rich()` 按顺序把它们拼进
同一个 `MessageChain`：文字段照发，表格与公式段各自渲染成 PNG 插在**原来的位置**，
再用现成的配额切分（长文本分页 + 图片配额）。识别规则：

- 表格：含 `|` 的表头 + 下一行是 `---` 分隔行；
- 公式：`$$…$$`、`\[…\]`，以及单独成行的 `$…$`；
- 缺分隔行的「伪表格」不认（避免把普通文本里的竖线误判）。

### 12.3.1 哪些块会被挑出来出图

挑块的判据是「**发出去会变成一堆符号**」。目前覆盖：

| 块 | 触发 | 不出图会变成 |
|----|------|-------------|
| `table` | 含 `|` 的表头 + `---` 分隔行 | 一堆竖线 |
| `math` | `$$…$$` / `\[…\]` / 单独成行的 `$…$` | 反斜杠与 `$` |
| `heading` | `###` ~ `######`（**只认 3 个及以上**） | 一串井号（实测截图里就是 `### MiniMax…`） |
| `list` | **连续 ≥2 行** `- ` / `1. ` | 一堆破折号 |
| `code` | ` ``` ` 围栏 | 反引号 |

三条边界都是实测定的：

- **标题只认 `###` 及以上**：`#` / `##` 与正文里的井号（`#1`、`C#`）太容易混，
  当标题会误伤；
- **列表要连续 ≥2 行**：单个 `- ` 开头多半只是正文里的破折号，拉出来单独出图
  会把段落切碎；
- **列表/代码块内的公式随整块出图**，不再各自出小图 —— 整块渲染本来就把它们渲染对了。

**正文里的行内公式（`$x^{0}$`）**也要单独出图：`split_rich_segments` 只挑整块，
正文段落会整段当文字发，里面的 `$…$` 就原样变成 LaTeX 源码（实测截图：
「常数函数通常并入幂函数（$x^{0}$）」）。所以文本段还要再过一层
`split_inline_math()`：按行内公式切成 `文 / 式 / 文…`（保序），公式各自渲染成
**紧裁小图**与文字交错进同一条消息。

> 各种块的出图宽度与留白按类型区分（`FRAGMENT_WIDTHS` / `FRAGMENT_PADDING`）：
> 标题这种一两行的块窄一点、留白小一点，否则会是一条很空的白带；
> 表格/列表该铺满就铺满。

裁图这件事最后落在 `png.py`：**按像素**找内容边界再裁，不靠页面报的尺寸。
理由是页面只能给「元素的盒子」，给不了「墨迹在哪」—— 按盒子裁出来的图
右边多 42px、下边多 30px 空白（`x^{0}` 的内容只有 22×21，图却有 68×55）。

| 函数 | 用于 | 行为 |
|------|------|------|
| `crop_to_ink` | 行内公式 | 四边都裁到内容 + 几像素气口（宽高都紧） |
| `crop_bottom_to_ink` | 整段公式 / 表格 / `//md` 整页 | **保持宽度**（该铺满就铺满），只去掉底部预留的空白 |

纯标准库实现（zlib + struct）：Chrome 出的 PNG 是 8bit 非交错、filter 0~4，
所以解码只要反推那 5 种 filter；编码用 filter 0。**同时解决了字体时序问题** ——
裁剪看的是最终像素，不再依赖「量的时候字体到位了没有」。

判定「有墨迹」的阈值取 250（而不是更低）：要把抗锯齿的浅色边一起收进来，
否则紧裁会把字形边缘削掉一圈。

**目标是「紧贴」**，所以留白分两层都收得很紧：

| 层 | 值 | 说明 |
|----|----|------|
| CSS 盒子（`FRAGMENT_PADDING`） | 表格/列表/标题 6px、代码 8px、整段公式 6px/10px | 留白主要在这里；带边框的块（表格、`\boxed`）不能给 0 —— CSS 边框画在盒子边界上，0 会让边框压在最外一像素 |
| 像素收口（`PAGE_PAD`） | 4px | 只做最后一点余量；不能给 0，KaTeX 的字形墨迹比元素盒子**稍微偏左**，0 会让字形压在边界上 |

行内公式更紧：页面 padding 1px/2px + 像素收口，实测四周 2~6px。

两类块的处理不同：**表格铺满整页宽**（它本来就该铺满），其余块（公式/列表/代码/
标题）按**内容宽度**排（`.wrap.tight` + `width: fit-content`）并右侧像素收口 ——
固定 720 宽会让一段短列表右边空 100 多像素（实测），与「紧贴」相反。

> ⚠️ 像素收口有个坑：切点必须先夹到图片范围内。`x1 + pad` 可能超过 `width - 1`
> （内容贴边时），那样切出来的行**比声明的宽度短**，写出的 PNG 行长度与 IHDR 不一致
> —— 解码时 filter 直接读到垃圾字节（实测报「未知 filter 255」，图看着是坏的）。

### 12.3.2 公式渲染不能依赖网络（KaTeX 自带）

公式排版用 KaTeX。**原先只挂 CDN，出过一次真事故**：JS 回来了、CSS/字体没回来，
KaTeX 把公式转成了 HTML 但没有样式与字体 —— 出图就是**一行原样 LaTeX**
（用户截图那张 244×33 的图，与当时的产物逐像素吻合）。这种失败最坑的地方是
**看起来像成功**：用户收到的是一张图，分不出「排版好的公式」和「没渲染的源码」。

两条修法：

1. **自带一份 KaTeX**（`plugins/ai_chat/katex/`：`katex.min.js` + `katex.min.css`
   + 20 个 woff2 字体 + MIT LICENSE）。`katex_assets()` 优先返回自带的 `file://`，
   缺了才退回 CDN。公式排版从此不依赖网络。
2. **失败必须看得见**：KaTeX 缺席（或单个公式报错）时，脚本给它打上
   `math-failed`，样式退成等宽 + 红底。**不能静默 return** —— 静默正是
   「源码看起来像正文」的根源。

> 升级 KaTeX 时要连字体一起换：CSS 里引用的每个 woff2 都必须存在，
> 否则字体 404、公式又会退成源码。回归基线见
> `test_markdown.py` 的 `[8.92]`（逐条核对 CSS 引用的字体文件是否齐全）。

### 12.3.3 没有定界符的公式也要出图

模型被要求用 `$...$`，实际仍会直接写裸 LaTeX：

```
标准椭圆 \frac{x^2}{25}+\frac{y^2}{9}=1 的顶点在 (±5, 0)
```

原样发出去就是一串反斜杠花括号（用户截图报过）。所以 `wrap_bare_latex()` 会在
**完全没有定界符**的文本里，把这类裸公式包成 `$...$` 再走同一条出图路径。

判据是**命令后面必须跟着花括号参数**（`\frac{}{}`、`\sqrt{}`、`\vec{}`…）：
这类命令边界明确（配对花括号到哪儿就是哪儿），而 `\sin`、`\pi` 这种裸命令
「该包到哪儿」只能猜 —— 猜错的代价是把用户的正常文字变成图片，所以**宁可漏**。

几个必须注意的实现点（都是实测踩出来的）：

* **花括号要按配对读**：根号里套分式（`\sqrt{1-\frac{9}{25}}`）有两层，
  用「非花括号字符」那种正则只会吃到内层第一段，把一条公式切成三段；
* **相邻公式要合并**：`$\frac{a}{b}$+$\frac{c}{d}$` 该合成一条等式，
  否则用户看到两张小图中间夹一个 `+`；合并只吃算术符号，顿号逗号不碰；
* **有定界符时一律不动**：那种情况下剩下的反斜杠更可能是转义字符
  （百分号、下划线、换行），不动比乱动安全；
* `\left(…\right)` 靠成对定界符界定，没有花括号参数，走单独一条分支，
  且要把紧跟的指数（`^2`）一起收进去。

> `$$…$$` 也一样：原先只认「单独成段」的写法，于是「椭圆：$$…$$」这种
> 出现在句子中间的会整串漏掉。现在 `$$` 与 `$` 同等对待，只是排版更大。

### 12.3.4 公式块的内容是**裸 LaTeX**，不能当 Markdown 再解析一遍

用户报「公式的渲染是错的」，出图是一张 **244×33** 的小图，里面是
`\frac{x^2}{4}+\frac{y^2}{16}=1` 的**原样源码**。看着像「公式长这样」，
其实是一次静默失败。

链路上有两段对「内容是什么」的理解不一致：

| 环节 | 它以为内容是什么 | 实际做的事 |
|------|------------------|------------|
| `find_rich_blocks()` | Markdown | 用 `_MATH_BLOCK_RE` 匹配 `$$…$$`，交出来的是 `m.group(1)` —— **去掉定界符的裸 LaTeX** |
| `build_fragment_html(kind="math")` | 也是 Markdown | 把内容再喂回 `markdown_to_html()` 重新解析 |

裸 LaTeX 在 Markdown 里就是个普通段落：

```python
markdown_to_html(r"\frac{x^2}{4}+\frac{y^2}{16}=1")
# → '<p>\frac{x^2}{4}+\frac{y^2}{16}=1</p>'     一个 math-* 类名都没有
```

而 `katex_head()` 是**靠嗅探 HTML 里有没有 `math-inline` / `math-display` 类名**
来决定引不引 KaTeX 的 —— 嗅不到，就一份 KaTeX 都不引（CSS、JS 全没有）。
于是这一页退化成一行 16px 的黑字，被紧裁成 244×33 发给用户。

关键教训是**这种失败没有任何信号**：出图不是空白，是一张「有内容、排版正常」
的图，从产物上完全看不出是渲染失败；后台也没有一条日志。
所以修法是两层：

1. `as_display_math()` 在 `kind="math"` 时把 `$$` **补回去**再解析 ——
   内容本来就是 LaTeX，不该被当成 Markdown 重新猜一遍；
   已经带定界符的（`$$…$$`、`\[…\]`）原样返回，幂等；
2. `katex_head(force=True)` 给「已经知道这就是公式」的调用方一个绕过嗅探的开关 ——
   嗅探只是省一次引用的优化，**不该成为唯一判据**：嗅探不中就等于静默不渲染。

> 判据上的坑：回归断言不能只看「图里有墨迹」。**一行源码也有墨迹**。
> 真正的判据是**墨迹高度**：`\frac` 排出来是上下两层的分式，必然比一行纯文字高
> 得多（实测 50px vs 17px）。对照组用同一段文本走 `kind="heading"` ——
> 同一套片段机制、但不按公式处理，保留的正是 bug 现场那副样子。

修完之后又冒出第二个问题：公式**居中排版**，而收口用的 `crop_right_to_ink`
写明「左侧不动，保留排版起点」—— 于是出图左边白 56px、公式被挤到右边。
所以 `FRAGMENT_CROP_ALL = {"math"}` 单独走 `crop_to_ink` **四边一起收**：

| 块 | 左边距 | 为什么 |
|----|--------|--------|
| 公式 | 4px（紧贴） | 它是居中、自身独立的一张图，左边距没有任何语义 |
| 列表 | 39px | 项目符号的缩进**是排版的一部分** |
| 代码 / 标题 | 保留原样 | 同上，左边距承载对齐信息 |

> 这个回归是**已有的** `test_images_are_tight` 抓到的（判据是「左边距 ≤ 30px」）：
> 修好渲染之后公式才第一次真的居中，左边距才暴露出来。要是只跑新加的用例，
> 会以为「渲染对了」就收工。

### 12.3.5 跨行的 `$…$`：`cases` 必须换行写，而换行 KaTeX 不认

用户截图报过：解方程组的这段整串原样发出去，`$`、`\begin{cases}`、`\end{cases}`
全是裸文本。

```
两条线的交点就是解方程组 $\begin{cases}
y = 2x + 1
y = -x + 3
\end{cases}$，可得：
```

**两个原因叠在一起**，缺一不可：

| # | 原因 | 修法 |
|---|------|------|
| ① | 行内公式正则写的是 `[^$\n]{1,200}` —— **换行被排除在外**，跨行的 `$…$` 一个都匹配不上 | `_MATH_BODY` 允许换行，但限 `_MATH_MAX_LINES = 6` 行 |
| ② | KaTeX 在数学模式里**忽略换行**，而 LaTeX 的 `cases`/`aligned`/矩阵要求行间写 `\\` —— 模型直接换行，于是渲染成一行挤三个式子 | `normalize_math_rows()` 把裸换行补成 `\\` |

两者都要有：只修①，公式认出来了但排版是错的；只修②，根本认不出这段是公式。

**行数上限不能省**：不限的话，正文里孤零零一个 `$`（价格、货币写法）会和几十行
之外的另一个 `$` 配成一对，把中间整段话吞进公式 —— 实测
`价格 $5\n\n下一段\n\n再来一个 $ 符号` 会被整段当成公式。补的两条约束是
「续行必须非空」（挡住跨空行的段落）与最多 6 行。已经写了对的
（`\begin{aligned} a &= 1\\ b &= 2`）不重复加，`\begin{...}` 与 `\end{...}`
前后也不加，免得公式开头凭空多一个空行。

### 12.4 行间公式（`$$…$$`）与超宽公式

`$$…$$` 是**独立于行内公式**的一条路，而且有三个坑：

| 坑 | 症状 | 做法 |
|----|------|------|
| 逐行处理 | `$$` 常常单独占一行、公式在中间行，逐行套跨行正则永远匹配不上 | 在 `markdown_to_html` 第一趟按**整段**识别（同一行起止 / 单独 `$$` 行两种写法），且要在行内公式**之前**、代码**之后** |
| 几何查询被裁 | 公式在行内盒**内部**溢出：容器 668px 而公式自然宽 **2703px**，而 `getBoundingClientRect` 与 `scrollWidth` **都只报容器宽** → 宽度自适应失效、右边被切 | 关掉 KaTeX 自带的 `.katex-display{overflow:auto}`（它连几何查询一起裁），并遍历**后代**取最右边界来量真实宽度 |
| 太宽放不下 | 2703px 的图在 QQ 里根本看不清 | 超过 `MAXW=1160` 时按**根字号**等比缩小（不能用 CSS `zoom`：会让 `getBoundingClientRect` 的坐标空间乱掉，实测墨迹只占左上角）；缩完再量最终尺寸 |

宽度定下来之后仍可能有偏差（容器定宽 + em 缩放会让量测飘），所以最后再用
`crop_right_to_ink` **按像素**把右侧留白收口 —— 量得准不准都不影响结果。

> ⚠️ 高度必须在 `document.fonts.ready` 之后量：KaTeX 的 web 字体没换上来时公式更矮，
> 量完再换字体就会把底部切掉（实测量到 279px、实际内容到 300+）。

> ⚠️ 还有个更隐蔽的坑：**Chromium 在视口过小时会整张画成空白**。
> 实测同一个页面，`720x156`、`720x170` 全白，`720x200` 起才画出来 ——
> 而公式图、行内公式图恰恰只有几十像素高。所以渲染统一按
> `MIN_SHOT_HEIGHT = 240` 的下限出图，再按像素裁掉多余留白。
> 对应的回归断言是「图里真的有墨迹」而不是「文件存在且够大」：
> 全白的 PNG 完全合法，只看文件大小是发现不了的。

`reply.inline_math=false` 可关掉这一层（行内公式就原样发文字），
用于「图片太多反而刷屏」的场合。

**提示词必须主动要求，否则能力等于白做**：默认人格原先写着
「`|表格|` 会原样显示成符号，很难看」—— 模型照做就不发表格。现在改成
`TABLE_MATH_GUIDANCE` 一段（嵌在人格里、两种模式都带）：

- 明确「需要对比/罗列/说明步骤时直接用 Markdown 表格」「有数学表达式就用 LaTeX」
  并告诉它**这两类会被渲染成图片**（模型知道结果会变好看才愿意用）；
- 给出**确切的写法**：`| --- |` 分隔行不能省（省了就不被识别），
  行间用 `$$…$$`、行内用 `$…$`，并列出常用命令（`\frac` `\sqrt` `\sum` `\int` …）；
- 提醒一次别超过 1~2 个，否则刷屏；
- 同时**仍然禁止**不会被渲染的那些（`**加粗**`、`#` 标题、代码围栏、`> 引用`），
  否则用户看到的是一堆符号。工具指引里也补了一句「把工具查回来的结构化信息
  整理成表格」，因为工具结果正是最该上表格的场景。

公式用 **KaTeX**（CDN）排版，取不到时 JS 会**原样显示 LaTeX 源码** ——
宁可让用户看到公式源码，也不能给一张空白图。

> ⚠️ TeX 是放在 `<script type="text/plain">` 里交给 KaTeX 的，所以**不能**
> 对它做 `html.escape()`：`<script>` 的内容不解析 HTML 实体，转义后 KaTeX 收到的是
> 字面量 `&amp;`，`cases` 的对齐符 `&` 就会渲染成 `amp;b = 0`（实测截图可见）。
> 只处理唯一真正危险的序列 `</script`（会提前闭合标签），其余原样保留。

**行内公式（`$…$`）是另一条独立的路**，走 `_inline()` 里的 `_stash_math()`：
先摘成 `<span class="math-inline">` 占位，再由页面里的 KaTeX 补渲染。三个坑：

| 坑 | 症状 | 做法 |
|----|------|------|
| 摘取顺序 | `x_0` 被斜体规则吃掉、`a[1]` 被链接规则吃掉 | 公式必须在 `_inline()` **之前**摘出来（与代码片段同一套 stash） |
| 单字符下限 | 结果列 `$1$`、`$0$` 整列漏掉（原正则要求 ≥2 字符） | 放宽到 1 字符，并用 `(?!\d)` 挡住 `$5 到 $10` 这类货币写法 |
| 渲染时机 | 公式全留成源码 —— `katex.min.js` 还没下载完就执行渲染脚本，`typeof katex === 'undefined'` 后静默 return | 渲染脚本**等 `load`**；逐个公式 try/catch，写错的那个留原文、其余照常 |

表格页（`build_table_html`）**也要引 KaTeX** —— 单元格里常有行内公式，
不引就整列显示成 LaTeX 源码。两处共用 `katex_head()`，且**只在片段里真有公式时**
才引，省一次 CDN 往返。
（本机 `/usr/share/yelp/mathjax` 那份 MathJax 2.x 只有 `yelp.js` 配置、
没有 TeX 输入，接进来渲染不出东西，已弃用。）

## 十三、函数图像（`plot_function`）

用户说「画个图看看」「这个函数长什么样」「画出 y=x²-4」，模型调 `plot_function`
把**坐标系 + 曲线**画成一张图发回来。

```
plot_function(expression="\frac{\sin x}{x}", x_min=-10, x_max=10)
plot_function(expression="x^2+y^2=25", x_min=-6, x_max=6)     # 方程（圆）
plot_function(expression="x=\cos(t), y=\sin(t)")             # 参数方程
```

`expression` 有**三种形态，自动识别**（不用声明）：

| 形态 | 写法 | 画法 |
|------|------|------|
| 一元函数 | `x^2-4`、`\sin(2x)`、`1/x` | 按 x 采样成折线 |
| **方程** | `x^2+y^2=25`、`\frac{x^2}{9}+\frac{y^2}{4}=1`、`x^2-y^2=4` | 求 `F(x,y)=0` 的等值线（见 [13.1](#131-版面两轴同标度格子是正方形) 下的「方程 / 参数方程」） |
| 参数方程 | `x=\cos(t), y=\sin(t)` | 按 t 采样（变量是 `t`） |

判定规则很简单：**带 `t` 且两半都写 `x=…, y=…` → 参数方程；含 `y` → 方程；
否则是一元函数**。`y=f(x)` 这种写法会被剥掉左值当一元函数。

| 参数 | 说明 |
|------|------|
| `expression` | 关于 `x` 的表达式，LaTeX 或普通写法都认；变量固定为 `x` |
| `x_min` / `x_max` | 横轴范围，默认 `-10` / `10` |
| `y_min` / `y_max` | 纵轴范围，**一般不用给**（自动适配，见下） |
| `x_step` / `y_step` | 刻度间隔（数据单位）。留空自动选；给了就是「每多少个单位一个刻度」 |
| `unit_px` | 一个数据单位画多少像素（= 格子多大，并把刻度定成 1 个单位）；留空铺满画布 |
| `t_min` / `t_max` | 参数方程里 t 的范围，默认 `0`..`2π`（要画多圈就加大，如 `4π`）|
| `equal_aspect` | 两轴统一标度 + 格子方正。**默认就是开的**；`false` 关掉，回到「纵轴按数据自适应、画布固定 460」的老行为 |
| `title` | 一行说明。**默认不显示在图上**（`plot.show_title` 打开才排）|

### 13.1 版面：两轴同标度，格子是正方形

**直接用 matplotlib 画**（之前是「自己算坐标 → 生成 SVG →
交给 Chromium 截图」，约两千行手写几何）。样式用 matplotlib 默认的那套：
四边框、刻度在外、轴标签在左下。

三件事现在是**一行代码**而不是一段推导：

| 要求 | 之前怎么做 | 现在怎么做 |
|------|-----------|-----------|
| 两轴标度相同 | 反解窗口长宽比、再反解画布高度 | `ax.set_aspect("equal", adjustable="box")` |
| 格子是正方形 | 两根轴各自吸附「好看数字」再挑最接近的比例（实测最差偏 14%） | 同上 + 两根轴挂**同一个** `MultipleLocator` |
| 紧贴裁剪 | 自己解码 PNG、逐行逐列找墨迹边界 | `bbox_inches="tight"` |

> `set_aspect("equal")` 是**数学上**保证的：matplotlib 让坐标系的「像素 / 数据单位」
> 在两根轴上严格相等。而「格子」要不方，还得两轴用同一个步长 —— 同一个步长乘以
> 同一个「像素/单位」就是同一个像素数。两条合起来，格子必然是正方形。

**默认步长就是 1 个单位**（用户要求原话「横纵坐标标度一定相同，默认为 1」）。
跨度超过 25 个单位才换 `1/2/5×10ⁿ` 的更粗步长，否则 `x∈[-100,100]` 会画成两百格。

> **验收口径**：渲染器会把每个面板的「像素 / 数据跨度」交出来（`out_probe`），
> 测试断言两根轴的比值 `== 1`（浮点意义上 `< 1e-9`）。**不在 PNG 上量网格线** ——
> 早先这么量过，坐标取整 + 像素栅格带来 0.3% 的假偏差，白查了一轮。
> 现在 15 个用例（含断轴、含 10:1 的扁椭圆）全部 `0.0000%`。

#### 窗口：由数据定，再收进画布能承受的长宽比

等比例意味着「纵轴能覆盖多少单位」由画布长宽比决定。所以窗口分两步：

1. 取数据的纵向范围（`y=x^2` 在 ±10 上是 `[0,100]`）；
2. 收进 `1.25 × 横轴跨度`（900px 上限 / 720px 宽）—— **超了就收窄窗口，不是压缩
   纵轴**。不收的话 `y=x^2` 会画成 1:5 的竖长条、`y=1000x` 更是 1:1000。

收窄时按三级判据摆窗口，顺序不能换：

① 数据跨零 → **居中于 0**（原点必须在窗口里，否则曲线穿过零轴的那段会被切掉）；
② 恒正 → 贴着数据下沿；③ 恒负 → 贴着数据上沿。

代价是曲线可能从顶端出去 —— 这是「真比例」的固有取舍，用户明确选了它：
**想看全就收窄 x 范围**，而不是关掉等比例。

#### 方程 / 参数方程

* **参数方程**：按 `t` 采样成折线（跟一元函数一样）。
* **方程（隐式）**：`contourpy` 提 `F(x,y)=0` 的等值线 —— 它就是 matplotlib 画
  `contour` 用的那个引擎，是 matplotlib 的硬依赖，**不引入新依赖**。比手写
  marching squares 省掉一整块几何代码。

三种曲线最后都归成**同一种形状**：一串 `(x 数组, y 数组)` 折线段。于是渲染只有
一条 `ax.plot` 路径，配色、线宽、图例都只有一份实现。

> `contourpy` 不收 `nan`：`y-\sqrt{x}` 在 `x<0` 无定义，那里要换成同号的大数
> （等值线自然穿不过去），而不是硬连一条线。

#### 多条曲线画在同一张图（`expressions`）

```
plot_function(expressions=["2*x+1", "-x+3"])
```

按 matplotlib 的默认配色环依次取色（蓝、橙、绿、红、紫…），**两条以上自动出图例**
（图例文字就是表达式）—— 有了图例，用户一眼就能对上哪条是哪条。

> 早先图里不写文字、也不给图例，颜色与表达式的对应只能由工具回执转告模型，
> 再让模型在正文里说「蓝色那条是 y=2x+1」。现在图例解决了这件事，
> 回执里**仍然**带一份颜色对照，两边都留着。

#### 坐标轴省略（断轴）

```
plot_function(expression="sin(x)+1000", omit_y="0..999")
```

用 matplotlib 官方的断轴画法：**两块面板 + 波浪线断口**。三种情形：

| 省略段相对窗口 | 结果 |
|----------------|------|
| 落在窗口**内部**（`x^2` 省略 `10..90`） | 上下两块面板，**面板之间那道缝上**画波浪线，并把相对的两条边框隐掉 |
| **紧贴窗口下方/上方**（`sin(x)+1000` 省略 `0..999`） | 一块面板，记号画在**纵轴**（左/右边框）靠那条边的一小段上 |
| 跟数据无交集 | 不省略 |

> ⚠️ 两种情况的记号**位置不一样**，这不是随意的：
> 省略段在窗口内部时，面板之间本来就有一道缝，波浪画在缝上一眼就是「轴在这里断开」；
> 而紧贴窗口一侧时**没有缝** —— 那时若把波浪画在整条底边上，它会正好压在**横轴**上，
> 看起来就成了「横轴在抖」（用户实际就这么问了）。所以改成在纵轴那一侧画一小段，
> 长度与摆幅按**像素**算（不随画布大小变形）。

> ⚠️ 第二种**不**把窗口撑到省略段里去。撑进去的话窗口会从 2 个单位变成 1001 个，
> 等比例下要画成 500:1 的竖条；而波浪线本来只是「这里跳过了一段」的记号，
> 不需要真把那一段画出来。这一条是刻意的 —— 上一版靠「把省略段压成
> 窄带」绕开了同一个问题，代价是纵轴标度在断口处不连续。

两块面板的高度按各自的数据跨度给，所以 `set_aspect("equal")` 在两块里解出的
「像素/单位」是同一个 —— **跨断口也仍然是统一标度**（实测 `0.0000%`）。

`omit_y` / `omit_x` 接受 `0..999`、`0-999`、`0~999`、`(0, 999)` 等写法。

#### 单位长度（`unit_px`）

保留着：一个数据单位画多少像素。等比例下它同时决定图的大小。

#### `MPLCONFIGDIR` 必须显式设

matplotlib 默认把字体缓存写到 `~/.config/matplotlib`，而这台机器的**根文件系统是
只读的** —— 不设的话每次都会退回临时目录、往 stderr 抱怨一句，缓存还得重建。
`_mpl_config_dir()` 会依次试：环境变量 → 插件自己的 `data/mplconfig` → 临时目录。

### 13.2 为什么现在用 matplotlib

早先不用它，理由很实在：**这台机器上一个画图库都没有**（matplotlib / numpy /
sympy / PIL / cairo 全缺），而 `history` 出图那条路已经有一整套 Chromium 管线，
于是函数图也蹭了同一条路 —— 自己算坐标、生成 SVG、交给无头浏览器截图。

那条路能跑，但**每加一个版面要求都要自己反解一遍窗口与画布**：「格子要正方」
推一次高度、「两轴要同标度」再推一次、「省略一段」又推一次，三者互相打架，
最后要靠 `_SQUARE_TOLERANCE = 0.22` 这类经验常数兜着 —— 实测 29 个函数里 26 个
格子偏差 >2%、最差 14%。圆还因为窗口取并集的 bug 一直画成椭圆。

后来能装了（cp314/aarch64 的 wheel 都齐），就换掉了。换完：

* `plot.py` 从 2756 行降到 ~1500 行，其中一半还是**没有变**的表达式解析与求值安全；
* 出图从「起一个 Chromium」变成纯 Python 调用，**快一个数量级**（0.1~0.2 秒）；
* Chromium 只剩 Markdown / 公式 / 历史卡片三条路还在用。

**保留下来的**是表达式解析（`latex_to_expr`）、求值白名单（`compile_xy`）、
形态判定（`parse_curve`）—— 那部分与「用什么画」无关，而且是安全边界
（表达式直接来自用户消息），不该跟着渲染一起重写。

**丢掉的**是上一版自己画的那套课本风：网格框、坐标轴伸出带实心箭头、轴名在端部、
原点标 `O`。这些是 matplotlib 默认样式里没有的，用户明确选了「换成默认样式」。

> 装的时候踩了一个坑：`venv-arm/bin/pip` 的 shebang 还指着**搬迁前的旧路径**
> （形如 `/home/旧用户/旧目录/...`），而那个路径在只读的根文件系统上 —— 直接跑
> `pip` 会装到旧 venv 并报 `Read-only file system`。要用
> `./venv-arm/bin/python -m pip install …`（解释器的 `sys.prefix` 是对的）。

### 13.3 求值安全：白名单，不是 `eval`

表达式**来自用户消息**，直接 `eval` 等于把 shell 送到群里。这里的做法是：

1. 先做 LaTeX → 普通写法的归一（`\frac{a}{b}` → `((a)/(b))`、`\sin` → `sin`……）；
2. 再用 AST **白名单**校验：只允许算术节点 + 数字常量，名字只允许 `x`、
   常量（`pi`/`e`/`tau`）与白名单函数；属性访问、下标、推导式、lambda、
   比较、布尔运算、位运算、字符串常量**一律拒绝**；
3. 即使这样，求值命名空间里也没有 `__builtins__`。

所以 `__import__('os').system(...)`、`().__class__.__bases__`、`open(...)` 这些
在解析阶段就被挡掉（回归基线见 `tests/test_plot.py` 第 3 组）。

幂运算另有一层限制：`x**x**9` 这种指数塔算出来是天文数字，**光是计算它就够把渲染
进程拖死**，所以指数超过 `_MAX_POW_EXP`（64）或结果绝对值超过 `_MAX_POW`（1e6）
一律判为「这里没定义」（`nan`），直接不画。

### 13.4 语法容错：能确定的才改写

用户的写法很杂（`2x`、`3\sin 2x`、`\frac{1}{2}x^2`、`\sin^2 x`、`y = x^2`、
`2.5e2`），所以归一阶段做了不少补全：隐式乘号、函数幂写法、裸参数、科学计数法。
原则是**能确定的才改写，不确定就报错**：

- 支持：`2x`、`3sin(2x)`、`x sin(x)`、`\sin x`、`\sin 2x`、`\sin^2 x`、
  `\log_{10}(x)`、`|x|`、`\sqrt[3]{x}`、`1e-3 x`、`y = …` / `f(x) = …` 前缀；
- 报错：认不出的 LaTeX 命令（`\zeta`）、非 2/10/e 的对数底数（`\log_3 x`，
  要按换底公式重写成 `log(x)/log(3)`）、未知名字。

> 为什么坚持报错而不是猜：猜错会画出一条**形状完全不对但看着挺像那么回事**的曲线，
> 用户没有任何线索发现问题。报错至少能让模型改一版重试。

### 13.5 四件容易画丑的事

| 问题 | 处理 |
|------|------|
| **奇点**（`\tan x`、`1/x`） | 相邻采样点跳变超过「纵轴量级 ×1.0」就**断开路径**，否则会出现一排竖直假线 |
| **尖峰压平曲线** | 纵轴按 2%/98% **分位数**取核心带，而不是最大最小值 —— 否则 `1/x` 在 0 附近的 ±1e6 会把整条曲线压成一条直线 |
| **原点被顶到边上** | 核心带跨零时**对称化**成 `±max(核心带半宽, 两侧最大伸展的一半)` —— `e^x/\sin x` 的核心带本是 [−690, +76]，横轴（画在 y=0）被顶到画面 90% 处，整张图看着是歪的；对称化后原点回到正中 |
| **刻度标签说谎** | 步长按 1/2/5×10ⁿ 取整；小数位由步长的**尾数**决定（`2.5` 要 1 位，否则 `-10` 会显示成 `-1`）；首尾标签改锚点，避免被画布切掉半个数字 |

> **2%/98% 是实测选出来的，不是拍的**：拿 14 个典型函数（多项式、三角、倒数、
> 指数、对数、根式、渐近线型）比过 2%/3%/5%/10% 四档 —— 2% 的数据覆盖率最高
> （渐近线型 95%、多项式 96%），收紧到 10% 会把 `x^3-3x` 压成 ±488（经典形状没了）。
> 真正解决「原点偏心」的是**对称化**，不是把分位带收紧。
> 单侧函数（`x^2`、`e^x`）**不做**对称化，否则范围无谓扩大一倍。

> ⚠️ **SVG 上不要加 `overflow="visible"`**：出图管线量高度的方式是遍历容器元素取
> `getBoundingClientRect` 的极值，而一个 overflow 可见的 SVG 会被算成**它的全部内容
> 范围** —— 极点处冲出画布的渐近线把页面高度从 460px 报成 5552px，出图变成一条被
> 纵向拉伸的长条（实测）。首尾刻度标签的裁切问题已由「改锚点」从源头解决。
> 回归基线：`test_plot.py`「SVG 不带 overflow=visible」「渐近线型曲线原点居中」。

公式用 KaTeX 排在图上（用的是**用户原本的 LaTeX**，不是归一化后的写法），
所以看到的式子和曲线是同一个。

### 13.6 图片怎么送到用户手里

工具结果只能是**文本**（客户端只发纯文本），没法把图片塞回模型上下文。所以：

1. 工具先把图渲出来，把路径写进一个占位标记 `[[plot:路径|标题]]` 一起返回；
2. 主流程跑完模型循环后，从**本轮新增的工具结果**里把标记取出来
   （`_plots_from_tools`），换成真正的图片节点，**图单独一条消息**发
   （QQ 的图片节点插在正文中间会把文字断成两截）；
3. 正文里剩下的部分照旧走「表格/公式出图」那条路。

> **为什么不从模型的正文里取标记**（这是实测踩过的大坑）：标记是工具写在返回
> 文本里的，而正文是模型自己生成的 —— **模型不会原样转述工具结果**，它会用自己的
> 话概括。实测会话记录：
>
> ```
> [tool]      RESULT:'…[[plot:/…/h-1791225134003-1.png|一次函数 y = 2x + 1]]'
> [assistant] TEXT:'画好了，是一条过 (0, 1) 的直线…'      ← 标记没了
> ```
>
> 图渲染出来了，标记却消失在模型的概括里，用户什么也收不到。图和标记本来就在
> **本插件自己的**工具结果里，直接从这里取，模型说什么都不影响。
> 只取「本轮新增」的那些（按消息条数圈定），免得把上一轮的图又发一遍。

> **标记必须只有工具能产生**：主流程只放行「本实例真的渲染过」的路径
> （`PlotService.rendered`）。模型被提示注入诱导、自己编一个 `[[plot:/etc/passwd]]`
> 是发不出图片的 —— 那等于把任意文件读出来发进群里。正文里若出现这种伪造标记，
> 只会被当成普通文字（或清掉），绝不会变成图片节点。
> 回归基线见 `tests/test_plot.py` 第 9 / 9.6 组，以及 `test_ai_chat.py` 的
> `test_plot_tool`（那里的桩**故意不转述**工具结果，就是为了钉住这个行为）。

渲染失败时**不留标记**，返回给模型的是失败原因（「图渲染失败（…）。可以先用文字
描述这个函数的形状，并说明图片暂时画不出来」），由模型如实告诉用户。

### 13.7 配置

```jsonc
"plot": {
  "enabled": true,
  "width": 720,        // 画布宽度（px）
  "height": 460,       // 画布高度（px）
  "samples": 1200,     // 采样点数（越多曲线越顺，越慢）
  "grid": true,        // 是否画网格线
  "x_step": null,      // 刻度间隔（数据单位）；null = 自动选 1/2/5×10ⁿ
  "y_step": null,
  "unit_px": null,     // 一个数据单位画多少像素（= 一个格子多大）；null = 铺满宽度
  "equal_aspect": null, // 两轴统一标度 + 格子方正；默认开，false 可关
  "omit_y": null,      // 纵轴省略一段（如 "0..999"）：折成一小条并画波浪线
  "omit_x": null,
  "show_title": false, // 图上是否排一行公式标题（默认不排：图里只有坐标系与曲线）
  "t_min": 0.0,        // 参数方程里 t 的范围（默认一个周期）
  "t_max": 6.283185307179586,
  "t_samples": 1200    // 参数方程的采样点数
}
```

`x_step` / `y_step` / `unit_px` 是**默认值**：模型在 `plot_function` 里显式给了
参数就用它的，没给才落回这里。所以运营侧可以定「这个部署统一每 1 个单位一个刻度」，
而模型仍能针对某张图临时改。

`plot.enabled=false` 时不注册这个工具，系统提示里也不提它（提了只会让模型空调用一轮）。

## 十四、`/md`：把上一条 AI 回复转成图片

```
/md
```

**顶层命令，没有子命令** —— 不带 `aichat` 前缀（日常用得最多的一句话动作，
值得少打几个字）。它取当前会话里**最后一条有正文的 AI 回复**，用
`render_markdown` 渲染成一张 Markdown 图片发回来。

| 行为 | 说明 |
|------|------|
| 渲染的是**会话里的原文** | 不是「上一次发出去的东西」—— 所以就算上一条回复当时是分页发的、或者走了纯文本路径，`/md` 拿到的都是完整原文 |
| 不调模型 | 纯渲染，不烧 token |
| 没有会话 / 还没回复过 | 各给一句说明，不静默 |
| 服务范围 | 仍然受限（与其它命令同一个守卫）—— 未开通的群/私聊用不了 |
| 发出去的图片也会记进索引 | 用户之后引用它，取回的仍是 Markdown 原文（见 [§4.3.1](#431-引用支持菊花链ai-的图片用原文替代)） |

> 为什么不做成 `/aichat md`：它和「管理会话」无关，是**对当前对话的一个动作**，
> 而且高频。命名空间留给低频的管理命令。

## 十五、网图配图（`fetch_image`）

用户说「来几张 xx 的图」，模型能搜、能读网页，但**发不出图** —— 它在正文里写
Markdown 图片或直接贴链接：

```
![](url)
```

QQ 里既不显示图片、用户还得自己点开 —— `fetch_image` 补的就是这一步：

```
fetch_image(url="https://…/cat.png", caption="一只橘猫")
```

链路与函数图像**完全同构**（工具产出文件 → 在 `rendered` 白名单里记一笔 →
主流程从**工具结果**里取 `[[plot:…]]` 标记 → 图作为**单独一条消息**发出）：

| 环节 | 位置 |
|---|---|
| 下载 | `search.WebClient.get_bytes()`（复用搜索那套 HTTP 客户端） |
| 校验 + 落盘 | `webimg.WebImageService.fetch()` |
| 工具 | `tools.register_image_tool()` |
| 取图 + 发送 | `main._plots_from_tools()` / `_send_plots()`（与函数图共用） |

### 15.1 四条安全边界（都是真会被利用的路径）

URL 来自**模型**，而模型刚读过不可信的网页与搜索摘要 —— 所以这里的输入等同于
「陌生人给的地址」：

1. **只允许公网 http/https**：复用 `search.check_url()` 的 SSRF 闸，而且
   **每一跳跳转都重查**。`get()` 走 aiohttp 的自动跳转（跳转目标不过闸），
   一个公网地址 302 到 `http://169.254.169.254/…` 就绕过去了 —— `get_bytes()`
   因此自己跟跳转（最多 5 跳，每跳 `check_url()`）；
2. **必须是真图片**：按**魔数**判定（PNG/JPEG/GIF/WebP/BMP），**不看后缀、不信
   `Content-Type`** —— 否则「下载这个 .png」就能把任意二进制塞进群里。不是图片
   会明确回绝，并提示「要读网页正文请用 fetch_page」；
3. **只有本插件下载过的文件才发得出去**：`rendered` 是白名单，模型自己编一个
   `[[plot:/etc/passwd]]` 在 `_plots_from_tools()` 里就被挡掉（与 `PlotService`
   同一条规矩）；
4. **文件名按 URL 哈希**（`sha1(url)[:20].<ext>`）：远程文件名是不可信输入，
   `../../etc/x` 这类名字进不了本地路径；同时让同一条链接天然去重。

另有三条工程约束：单张 `max_bytes`（默认 8MB，**超限直接拒绝而不是截断** ——
半张图发出去比不发更糟）、一轮 `max_per_turn`（默认 3 张）、目录 `keep_files`
（默认只留最近 60 个文件，防止 SD 卡被写满）。

### 15.2 配置

```jsonc
"web_image": {
  "enabled": true,
  "max_bytes": 8388608,   // 单张上限，超过就拒绝（不发半张图）
  "max_per_turn": 4,      // 一轮最多配几张（与 reply.chunk_max_images 对齐）
  "keep_files": 60,       // 落盘目录只留最近多少个文件
  "page_images": 6        // fetch_page 顺带列出几条页面图片直链
}
```

> 依赖 `search.enabled`：下载复用搜索的 HTTP 客户端与 SSRF 闸。关掉搜索
> （或 `web_image.enabled=false`）时**工具与提示词一起消失** —— 讲一个模型调不到
> 的工具，只会让它空转一轮。

### 15.2.1 模型**怎么找到**图片直链（这条最容易做错）

工具能下载不等于用得上 —— 模型得先拿到**直链**。第一版没管这件事，线上实测
（用户问「给出这几种封装的图片」）表现是：

```
22:31:28  web_search ×3        → 只拿到一堆网页链接
22:32:05  fetch_page ×3        → 纯文本里看不到 <img>，一无所获
22:32:36  web_search ×2        → 再来一轮
22:32:53  fetch_page + search  → 再来一轮
22:33:13  fetch_page ×2        → 知乎 403、期刊页无关
22:33:27  web_search ×2        → 第 6 轮，轮次用尽
```
用户最后只收到一句 **「（已达单轮上限 6 次模型调用，先说到这里）」**，一张图没配上、
一个字没说。两个根因，都补掉了：

1. **纯文本里没有图片** → 两条信息通道：
   * `fetch_page` 现在会在正文后面附上**页面里的图片直链**
     （`search.page_images()`：认 `src` 与懒加载的 `data-src`/`data-original`，
     相对路径用 `urljoin` 补全，丢掉 `data:`/`svg`/占位图/图标，去重、限量）；
   * 搜索 API 若自带图片字段（`image`/`thumbnail`/…）会在结果里直接写成
     「图片直链（可直接 fetch_image 下载）：…」（`SearchResult.image`）。
2. **轮次全被工具吃掉** → `_model_loop` 的**最后一轮不带工具**，并在系统提示里
   明说「工具次数已用尽，请直接用已有信息回答」。这样无论模型怎么绕，用户至少
   能拿到一句真话（哪部分没查到），而不是只看到「已达上限」。

提示词里也把路径写死了：**读两三个页面还没有直链就直接说清楚**，别再读页面。

### 15.3 提示词怎么交代

`compaction._IMAGE_GUIDANCE` 只在能力开启时追加，四条：① 要图时用**直链**（先搜，
拿到网页用 `fetch_page` 找直链）；② 图会**单独一条消息**发，正文里**不要**再写
`![]()`/`<img>`/裸链接（QQ 显示不出来），用一两句话说明这张图是什么；
③ 只配真有帮助的图，一轮最多几张；④ 失败（太大/不是图片/链接失效/内网地址）
如实说明原因，可换链接但别反复重试同一个；⑤ 别用它下网页（那是 `fetch_page`）
或文件（`.zip/.pdf/.exe` 一律被拒）。

### 15.4 测试

* `tests/test_webimg.py`（48 项）：魔数判定、SSRF 闸、跳转逐跳过闸、超限报错、
  一轮张数、同 URL 去重、目录有界、白名单；
* `tests/test_ai_chat.py::test_fetch_image_tool`：端到端 —— 工具出现在模型看到的
  清单里、调用后图片真的作为单独一条消息发出、系统提示里讲了怎么用、关掉开关
  后工具不再注册。

## 十六、结束符

**结束符的语义是「这一大段提交上去」**，不是「这一条消息发完了」。

输入可能长得超过单条 QQ 消息的上限，用户就分几条发；每一条先落在暂存区，
最后发一个结束符把它们**按顺序拼成一整段**交给模型。拼接是**直接按换行拼**、
**不加任何序号**：

```
用户：帮我画个图           ← 暂存
用户：y=sin(x)+1000，      ← 暂存
用户：x、y 每格 1 个单位    ← 暂存
用户：//                   ← 提交：上面三条拼成一段
```

> 早先会拼成 `(1/3) 帮我画个图`、`(2/3) …` 这样，本意是告诉模型「这条被客户端
> 截断了」。但序号**不是用户写的**，而且会诱导模型在回复里模仿同样的编号
> （提示词里专门叮嘱过「不要写 `(1/3)` 这类分段标记」，那就更不该由插件自己造）。
> 分段之间的换行保留 —— 那正是用户实际敲下的位置。

识别规则：

- **行尾**匹配（`你好//`、`你好 //`、`你好\n//` 都算），中间出现不算；
- 单独发一条也行；
- `terminators` 支持多个（如 `["//", "。。"]`）。

> ⚠️ **`trigger.auto_submit_seconds` 目前是死配置**：文档与 `config.json` 都写着
> 「>0 时静默这么久自动提交」，但代码里**没有任何地方读它**。保持 `0`（不启用）
> 时无影响；要用得先把它实现出来（需要一个按目标计时的任务，并在补发/显式提交/
> 插件卸载时取消）。这也是 `staging.json` 里积着好几个用户「发了半截没提交」的
> 原因 —— 他们不会再来补那个结束符。

> **已退役：`/end` 命令形式**（曾有一条顶层 `/end` 命令，文档里还写过别名 `/eot`、`/finish`
> —— 那两个别名代码里从未存在）。两条入口维护同一件事，行为迟早分叉：命令形式不吃行尾
> 的 `//md`（Markdown 后缀），也不走 `_strip_terminator`。现在**只有行尾结束符一条路**，
> 发 `/end` 会当普通消息进暂存区（不会提交），必要时用行尾 `//` 收尾。

### 16.1 暂存区按「跟谁说话」存，不按「从哪个窗口打字」存

**症状**：在一个窗口里分段发了一大段，在另一个窗口里发 `#`，回「暂存区是空的」，
而且那段内容**再也提交不了**。

**根因**：暂存区原来用 `ChatTarget.key` 当键，而群临时会话（小窗）的 key 是
`private:<uid>@group:<gid>` —— 同一个人在「主私聊」和「群小窗」里打字会落到
**两个不同的暂存区**。线上 `staging.json` 里就明明白白躺着同一个人的两个键：

```
private:100000005@group:100000002   2 段
private:100000005                   4 段
```

**同一个 bug 也在会话焦点上**：`focus_key` 原先也建在 `chat.key` 上，所以换个窗口
说话就「本群暂无会话」。

**修法**：`ChatTarget` 分出两个概念，别再混用：

| 属性 | 含义 | 用途 |
|------|------|------|
| `key` | **往哪儿发**（含小窗的来源群） | 发送、绑定表里的标识 |
| `conversation_key` | **跟谁的对话**（私聊只认 uid） | 暂存区、会话焦点、并发闸、待提交标记、回绝冷却 |

`group_id` 仍然留着 —— 它只决定回复发回哪个窗口。暂存区与焦点改用
`conversation_key`，两处一起改（同一个根因，只修一处还会撞上另一处）。

**老状态要迁移**，不能改完键就当没这回事：

* `staging.json` 里 `private:<uid>@group:<gid>` 的条目**并进** `private:<uid>`
  （内容追加在主键原有分段之后）；
* 绑定表里 `private:<uid>@group:<gid>@user:<uid>` 的焦点键并成
  `private:<uid>@user:<uid>`；主键已有值时**保留主键**（那是用户在主私聊里选的）。

> 线上验证：迁移后 `private:100000005` 从 4 段变成 **6 段**（并进了小窗那 2 段），
> 内容没丢。回归用例 `test_staging_shared_across_windows` 与
> `test_window_key_migration`。

### 16.2 上一轮还在回答时按结束符

用户截图报过：「发了内容、又发了结束符，却收到『暂存区是空的：先发内容』」。
底下是**三个 bug 叠在一起**：

| # | 症状 | 原因 | 修法 |
|---|------|------|------|
| ① | 发了内容 + 结束符，**什么都不发生**（不回答、不报错、后台无日志） | `_schedule_submit` 撞上 `_inflight` 时直接 `return` —— 既不提交也不记下来，内容永远卡在暂存区 | `_pending_submit` 标记；本轮 `finally` 里补提交 |
| ② | 回答期间再按一次结束符 → 回「暂存区是空的：先发内容」，用户以为白发了一遍 | 只发结束符时**一律**回这句，没有区分「真的什么都没发」和「刚才那段正在回答」 | 分三种情况：有暂存内容 → 直接提交；无内容但在回答 → 「刚才那段已经收到了，正在回答中」；其余才回「暂存区是空的」 |
| ③ | 只按提交键会往暂存区塞一个**空段** | 走的是同一条 `_stage(body="")` | 只按提交键时直接 `_schedule_submit`，不入暂存区 |

> ③ 的危害容易被低估：空段会被当成一段**真实输入**拼进去，模型看到一次提交里
> 多出一段空白，会以为用户想说什么没说。

复现与回归：`test_submit_while_busy`（慢速桩模型 + 真事件总线），断言
「第二段真的提交给了模型」「只按结束符不会塞空段」「回答期间的回执不说暂存区为空」。

> 实现细节：`//` 与命令前缀 `/` 天然冲突。框架已修正为「纯前缀不是命令」，
> `//` 会被判为非法输入**静默丢弃**（而不是回一句「未知命令: //」），
> 由插件当作结束符处理。回归基线见 `tests/test_command_parser.py`。

### 16.3 粘代码时**不用**给 `#` 加转义

用户报过：他往会话里粘一段 C++，为了不让开头的 `#include<bits/stdc++.h>` 被当成
命令（本部署里 `#` 既是命令前缀又是结束符），自己补了个反斜杠写成 `\#include…`，
结果模型收到的是带反斜杠的代码，于是答「第一行有个多余的反斜杠，编译不过」。

**这个转义是多余的**，框架本来就不会误判：

| 文本 | `CommandParser.parse()` | 结果 |
|---|---|---|
| `#aichat attach xcpc` | `command="aichat"` | 真命令，交给命令系统 |
| `#include<bits/stdc++.h>` | `illegal=True`（`命令名不是合法标识符`） | **静默丢弃**，插件当普通对话处理 |

判据是 `CommandParser._NAME_PATTERN = [a-zA-Z][\w-]*`：命令名里出现 `<`、`(`、`.`、`/`
就不是命令。所以代码原样发即可，既不会回「未知命令」，也不会被插件忽略。

但**用户已经这么写了**，而那个反斜杠会一字不差地进模型 —— 所以 `_unescape_prefix()`
兜一层：**行首**（允许前导空白）+ 一个反斜杠 + 紧随其后的「记号」（命令前缀或本插件
的结束符，见 `_escape_targets()`）→ 脱掉反斜杠。只认这一个形状，`$\#$`、`\dfrac`
这类 LaTeX 写法不受影响（回归见 `tests/test_ai_chat.py::test_escaped_prefix_paste`）。

### 16.4 结束符要等「还在读引用」的那条消息

**症状**（用户截图，2026-10-09 21:40）：先发了一条「重试 + 引用原问题」，两秒后发 `#`，
收到 **「暂存区是空的：先发内容…」**；更糟的是那段内容随后悄悄进了暂存区，
**再也不会自己提交**，用户得再按一次结束符。

**根因**：读引用要走 `get_msg`，而框架给**每一次** API 调用都加了 `api_delay`
（线上配的 1~5 秒）并串行化 —— 引用一条消息、再追它的引用链（最多 3 层），
几秒钟就过去了。这两条消息是**并发**处理的，所以「结束符」完全可能先跑到：

| 时刻 | 事件 |
|---|---|
| 21:40:36 | 用户发「重试 + 引用」（**开始消化**：要两次 `get_msg`）|
| 21:40:38 | 用户发 `#` → 此刻暂存区**确实是空的** → 回「暂存区是空的」|
| 21:40:39 | 上一条终于落进暂存区（`staging.json` 里的 `ts`）→ 卡住不动 |
| 21:40:41 | 用户收到「暂存区是空的」|

**修法**：把「从收到消息到落进暂存区」这段窗口显式标出来（`_ingesting[key]` 计数），
结束符只发一条时若发现**还有别人在消化**（计数 > 1，自己算一次），就轮询等它落盘
（`_await_pending_content`，上限 `_INGEST_WAIT_MAX = 30s`），等到就正常提交。
判据是「计数归 1」而不是死等超时 —— 别人消化完（可能是被拒绝、被当命令丢掉）
就立刻按真实情况回话，不浪费用户 30 秒。

> 只是等一等的话，为什么值得单写一节：这条竞态的窗口**由框架的节流决定**
> （`api_delay` 调大，窗口就变宽），而且失败表现是「用户明明发了内容却说没发」，
> 极难自查。回归用例 `test_terminator_waits_for_ingest` 里特意留了一条**反证**：
> 把 `_await_pending_content` 换成「直接返回空」的桩，同样的时序就会复现那句
> 「暂存区是空的」—— 保证这条用例不会变成摆设。

## 十七、持久化与并发

**配置在 `config.json`，状态在数据目录** —— 分开的理由：`config.json` 是人的领域
（改一次要 review），会话状态是机器的领域（每句话都在写）。混在一起会让每句对话都
重写一次核心配置文件。

```
plugins/ai_chat/data/
├── staging.json            未提交输入的暂存区（重启不丢）
└── sessions/
    ├── state.json          会话索引 + 绑定表
    ├── s0001.jsonl         每个会话一个 append-only 历史
    └── s0001.jsonl.deleted 删除后改名（可人工找回）
```

- **暂存区落盘**：用户可能在「@我 + 长文 + 结束符」之间隔几分钟，期间
  [看门狗](ncqq-watchdog.md#一它做什么)会主动重启 —— 内存态会让整段输入消失。
- **历史 append-only + 定期裁剪**：只在超过 `history_max_messages × 1.5` 时重写一次，
  避免每加一条消息就整文件重写（SD 卡写放大）。
- **每会话一把 `asyncio.Lock`**：同一会话的对话串行化，避免两条消息同时进模型。
- **`state.json` 用 `threading.Lock`**（锁内无 `await`）：事件处理、定时任务、
  卸载可能在不同 task 里调用。

ApiClient → WS` 全链路；只把「外部 LLM」换成本地脚本桩（否则测试要联网、要花钱、
还不稳定）。每个用例一个全新实例（独立 `data_dir`），互不污染。

## 十九、插件包内的 import 纪律

这一节是踩坑记录，改 `plugins/ai_chat/` 之前请先读。

### 19.1 不许有「函数内相对 import」

插件是被 `spec_from_file_location("napcat_plugin_ai_chat", …)` 加载的，
包名是合成出来的。热重载时 `PluginManager.reload()` 会把
`napcat_plugin_ai_chat*` **整棵子树**从 `sys.modules` 摘掉再重新导入。
此时如果一个函数**在调用时**才去 `from .llm import err_text`，Python 会重新解析
父包 —— 拿到：

```
ModuleNotFoundError: No module named 'napcat_plugin_ai_chat'
```

而它发生在**一轮对话中间**（工具执行 / 异常处理里），用户只看到
`⚠️ AI 对话出错（E-xxxx）：ModuleNotFoundError…`，完全看不出是热重载引起的。

**规则**：包内 import 一律写在模块顶层。顶层写完，模块加载时解析一次并绑定到
模块全局，之后函数调用只做属性查找，不再碰 `sys.modules`。

回归保护：`tests/test_ai_chat.py` 的 `[30]` 用例会把包从 `sys.modules` 摘掉后
跑完一整轮（含工具失败 + 压缩），并静态扫描源码禁止函数内相对 import。

### 19.2 不许跨插件加载（历史教训）

本插件曾经有一个 `_load_sibling_module("bupt_news", "weather")`：按文件路径去加载
**兄弟插件的子模块**。它存在的原因是相对 import 在任何加载方式下都不成立 ——

* 本插件叫 `napcat_plugin_ai_chat`，`..bupt_news` 会被解析成
  `napcat_plugin_ai_chat.bupt_news`（不存在）；
* `plugins/` 目录**没有** `__init__.py`，`plugins.ai_chat` 也不是正规包。

**这个补丁连同它服务的天气工具一起删掉了**，因为它是在跟框架边界对抗：绕开 import
系统去别人的包里取代码，等于把「两个插件」变成了「一个插件的两个目录」。现在插件之间
零耦合（见 [8.1 与其它插件彻底解耦](#81-与其它插件彻底解耦)），这条纪律是：

> 需要别的插件的数据或能力 → 让对方向外暴露 HTTP 接口，本插件用 `tools.custom` 接；
> 不要按路径加载别人的模块，也不要读别人的数据文件。

### 19.3 相对路径配置的统一口径

`data_dir` 走 `_resolve_relative()`：

| 写法 | 基准 |
|------|------|
| 留空 / 裸名字（`data`） | 插件包目录（插件自带的数据放插件里） |
| 显式相对（`./data/ai_chat`、`../shared`） | `config.json` 所在目录（从顶层配置写路径的直觉预期） |
| 绝对路径 | 原样使用 |

> 当年 `notices.path` 与 `data_dir` 共用这套规则，是因为前者默认值写的是
> `./plugins/bupt_news/data` —— 若按「相对插件目录」解析会变成
> `plugins/ai_chat/plugins/bupt_news/data`，一个永远不存在的路径。那段配置
> 已随解耦删除，但**规则本身要保留**：从顶层 `config.json` 写相对路径，
> 预期基准就是 `config.json` 所在目录。

## 二十、为框架做的改动

实现过程中发现若干框架层问题，都在 `napcat/` 内修掉了（不是插件 workaround）：

| 文件 | 改动 | 原因 |
|------|------|------|
| `napcat/command.py` | 新增 `CommandParser.strip_prefix()` / `skip_prefix()`；纯前缀（`/`、`//`）不再被当成命令名 | 旧实现把 `//` 解析成「名为 `/` 的命令」，用户每次发结束符都收到「未知命令: //」 |
| `napcat/command.py` | 命令名必须是合法标识符（`[a-zA-Z][\w-]*`），否则判 `illegal` | `//`、`/ /` 这类「前缀后跟分隔符」是垃圾输入，应静默丢弃 |
| `napcat/config.py` | 新增 `PluginConfig.all()` | 插件读整段配置原本只能 `get("")`，而它会返回 `None`（`get("__all__")` 也读不到），是个静默陷阱 |
| `napcat/plugin.py` | 插件生命周期改为**幂等**：`unload()` 强制解绑离场实例的监听器；`on_disable()` 只撤销「上次启用后新增的那一段」 | 热重载「新版本加载失败 → 回滚旧实例」会再调一次 `on_enable()`，而 `EventBus` **不按 hid 去重**，于是 `/events` 里同一个插件出现两对监听器、每条群消息被处理两次（实测每回滚一次多一份） |
| `napcat/command.py` | 新增 `/help` 可见性过滤器 `add_visibility_filter()` | 框架的可见性判据只有「scope + permission」；插件还有「本群是否开通服务」这类条件。没有钩子，插件只能自绘 help，于是同一份命令清单有两条渲染路径 |
| `napcat/command.py` | 命名空间下未知子命令返回「未知命令」，不再回落到父命令本体 | `/aichat help`（子命令已删）原本会执行注册子命令时自建的占位 handler，而它的 `lambda p: None` 签名与框架注入的 `event` 不匹配 → TypeError 被吞成「没反应」 |
| `napcat/config.py` | 新增 `PluginConfig.set_all()` | 补齐配置模板要写几十个键，逐键 `set()` 会每键全量重写一次 `config.json` |
| `napcat/config.py` | 新增 `ConfigManager.reload()` | 原本只在构造时读一次文件，「改了 config.json 不生效」无从解释；现在手工改文件可用 `/aichat reload --confirm=true` 显式重读 |
| `plugins/ai_chat/llm.py` | `LlmClient.reconfigure(*, reasoning_policy=...)` 走显式关键字 | 它在构造器里是从 `reasoning_effort` 派生的，不在初始字段里 —— 靠 `hasattr` 兜底的通用循环会把它静默丢掉（「改了配置但思考强度没变」） |

回归保护：`tests/test_command_parser.py` 钉住全部解析口径、`PluginConfig.all()` 与
`ConfigManager.reload()` 语义。
