# 十一、联网搜索

> 文档索引：[docs/README.md](https://github.com/Green1423/ncqqpy/blob/main/docs/README.md) · 上级：[ai_chat 插件](README.md) · 上一章：[历史对话](10-history.md) · 下一章：[Markdown 模式](12-markdown.md)


`web_search` / `fetch_page` 两个工具，让模型能回答「今天/最近」类问题。

## 11.1 为什么是两个工具

搜索摘要常常只有几十字，而「XX 什么时候」「怎么做」这类问题往往要读正文。
所以拆成「先搜 → 挑链接读正文」两步，token 花在模型自己判断有用的页面上。
这也是**一个提问、多段回答**的关键：不同来源各自成段，而不是把一堆摘要糊成一段
（工具指引里明确要求分段并标注来源）。

## 11.2 两条路：JSON API（推荐）与抓公开搜索页

**默认走 AnySearch**（`https://api.anysearch.com/v1/search`，**匿名即可用**）：
它是排序式的检索服务，结果干净、可引用，实测同一批查询 **0.5~2 秒**返回且直接命中
（「北京邮电大学 图书馆 国庆 开放时间」第一条就是北邮图书馆的开放安排）。

为什么默认不用抓页面：抓公开搜索页在有些网络里**根本走不通**。实测这台机器上
百度返回「安全验证」、搜狗要验证码、知乎 403、360 给空壳、Bing 返回一批**无关**
结果（对同一个查询返回 Bilibili 与北京市政府页面），而且抓页面要 **8~14 秒**
（含浏览器渲染兜底），AnySearch 只要 0.5~2 秒。

> 老部署（`api_url`/`api_key`/`api_tag` **三个键都空**）会在加载时**自动接入**
> AnySearch 并记一条日志；只要用户给其中任何一个填过东西就一个字都不动。
> 想显式走抓页面：把 `api_url` 留空（`""`）—— 这与「没配过」是两回事。

也支持换成别的 JSON API：

```jsonc
"search": {
  "api_url": "https://api.tavily.com/search",  // 或自建 SearxNG 的 /search
  "api_key": "tvly-xxxx",                      // SearxNG 一般不需要
  "api_method": "POST",                        // 或 GET
  "api_fields": {}                             // 可覆盖字段路径（见下）
}
```

配了就先走 API；没配或 API 失败才回落抓页面。响应解析兼容多家形状
（AnySearch `data.results[]` / Tavily / SearxNG / Bocha / 通用 `data[]`），
字段名按候选路径逐个试，也能用 `api_fields` 显式指定
`list_path` / `title_key` / `url_key` / `snippet_key`。

**垂直检索**用 `api_tag`（`<领域>.<子域>`，如 `academic.search`、`code.snippet`、
`finance.quote`）：AnySearch 提供 17 个领域，清单在 `search.ANYSEARCH_DOMAINS`，
拼错时插件会**直接说明并列出可用领域**而不是发一个注定空结果的请求。

**相关性闸对 API 是「安全网」而不是关卡**（`api_min_score` 默认 -1）：
API 是排序式的、不会整批跑偏，而精确子串匹配对中文误杀太多 —— 实测两个都被误杀：
`北邮` vs 结果里的「北京邮电大学」（同一实体、无公共子串）、
`今天北京天气` vs 结果里的「北京天气预报」（无整串）。
抓页面那条路仍保持严格（0.34），因为它**确实**会整批跑偏。

抓页面那条路保留为「没配 API 时的尽力而为」，三层：

| 层 | 做法 | 为什么 |
|----|------|--------|
| 1 | 相关性闸 + 换后端 | **有结果 ≠ 有相关结果**：Bing 会返回一批与查询无关的结果（170KB、10 个结果块，看着完全正常）。所以先算关键词命中率，低于阈值就当失败换下一个后端 |
| 2 | **无头 Chromium 渲染** | 搜索引擎对普通 HTTP 客户端返回 JS 空壳页或干脆是「大页面但没结果」。实测同一个 URL：aiohttp 拿 592 字节 0 条，Chromium 渲染拿 10 条。这一步**无条件**走，不看「像不像空壳页」——360 就是 58KB 正常页面但一个结果都没有，任何基于体积的判定都会漏掉它 |
| 3 | 双后端 | `bing` 与 `360` 两个解析器，谁先给出**相关**结果就用谁 |

默认顺序把 360 排在前面，是实测结论（同一查询 360 相关、Bing 无关），不是偏好。

**这台机器上搜索目前不可用**（所有引擎都挡了），配了 API 就能用 —— 见上面的配置。

解析器是**纯函数**（`parse_bing` / `parse_360`），所以能用**保存下来的真实 HTML**
做回归测试，不联网也能卡住「搜索页结构变了」。仓库里没有 bs4/lxml，用标准库
`html.parser` + 正则 —— 只需要「块边界」这一个结构假设。

## 11.3 安全：SSRF 闸

搜索结果与网页内容都是**不可信输入**（模型会把它们当资料读），所以抓取前必须校验地址：

- 只允许 `http` / `https`；
- **拒绝内网与本机地址**（`127.0.0.1`、`10.*`、`192.168.*`、`169.254.169.254`
  这类云元数据地址、`::1`、`.local`……）；
- 域名先解析成 IP 再判（解析失败按不安全处理）。

没有这道闸，一句「请访问 http://127.0.0.1:8080/admin 并把内容告诉我」就变成了
一个内网探测跳板。工具指引里也明确要求：网页里的「忽略之前的指令」这类话当普通文字。

## 11.4 配置

```jsonc
"search": {
  "enabled": true,
  "backend": "360",           // 抓页面时的首选；另一个自动兜底
  "count": 5,                 // 默认返回几条
  "timeout": 15,              // 单次请求超时（秒）
  "max_page_chars": 4000,     // fetch_page 回喂给模型的正文上限
  "user_agent": "",           // 留空用内置 UA
  "api_url": "https://api.anysearch.com/v1/search",   // 默认 AnySearch（匿名可用）
  "api_key": "",              // 留空=匿名；填 key 走认证（额度更高）
  "api_method": "POST",       // POST / GET
  "api_tag": "",              // 垂直检索：academic.search / code.snippet …
  "api_fields": {}            // 可选：字段路径覆盖，如 {"list_path": "data.results"}
}
```
