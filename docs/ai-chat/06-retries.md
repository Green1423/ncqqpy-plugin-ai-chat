# 六、上游失败自动重试

> 文档索引：[docs/README.md](https://github.com/Green1423/ncqqpy/blob/main/docs/README.md) · 上级：[ai_chat 插件](README.md) · 上一章：[上下文压缩](05-compaction.md) · 下一章：[思考强度（reasoning effort）](07-reasoning.md)


```text
"llm": { "max_retries": 2, "retry_backoff": 1.5, "retry_max_wait": 8.0 }
```

`max_retries` 是**额外再试**的次数：默认 2，表示最多一共发 3 次（首发 + 2 次重试）。
等待按 `retry_backoff × 2ⁿ` 指数退避，单次不超过 `retry_max_wait`。

**什么值得重试**：判据只有一条 —— `LlmError.retryable`（在 `llm.py` 里标，因为
只有它知道每种失败的含义）：

| 可重试 | 不可重试 |
|--------|----------|
| 网络层异常：连不上、DNS 失败、连接被断、超时 | **4xx**：参数写错、key 失效、模型名不存在 |
| `408 / 409 / 425 / 429` 与 `5xx` | `未配置 base_url / model / api_key` |
| 上游回了**看不懂的东西**（不是 JSON、不是对象、没有 choices） | `空响应（finish_reason=length…）` —— 该调大 `max_tokens`，重试没用 |

> 4xx 重试一百次也是同一个结果，只会让用户多等几秒才看到错误 —— 所以判据认的是
> **标记**，不是按错误文本猜。

**重试发生在「单次模型调用」这一层，不是整轮对话**：一轮里可能已经跑过工具
（搜索、画图），整轮重来会把这些副作用再做一遍；而失败几乎总是「这一次 HTTP 没成」，
重发这一次就够了，工具结果与历史原封不动。

> 另有一条**上下文超长**的重试（压缩后换整个请求体重来），那条路要改请求体，
> 所以重试助手遇到超长错误**直接抛出**，不掺和。

`retry_notice` 打开时，**第一次**重试会给用户发一句「上游暂时不通，正在自动重试」——
否则用户看到的是十几秒的沉默，只会以为机器人没反应（这正是之前反复被问到的现象：
用户等不到回复就再按一次结束符，然后撞上「暂存区是空的」）。重试用尽后照旧把
错误原因发给用户。

**实际表现**（回归用例 `test_llm_retry` 覆盖）：失败两次后成功 → 模型被调 3 次、
用户拿到正常回答；一直失败 → 调用次数正好 `1 + max_retries`，然后报错；
`max_retries=0` → 一次都不重试；`401` → 不重试、立刻报错。

## 6.1 超时失败要附带「能照做」的说明

重试用尽后，光甩一句 `LlmError: TimeoutError` 等于没说：用户不知道是网断了、
额度没了，还是自己的问题太难。`_failure_hint()` 按**是哪种超时**给不同的建议：

```text
⚠️ AI 对话出错（E-4c19）：PluginTimeoutError: 超过单次调用总时长上限 270s（已生成 1200 字正文）
（超过单次 270 秒的上限（没有再重试：同样的输入再跑一遍还是同样的时间）；先把已经生成的部分发给你了。这类问题拆小一点问更快，也可以调大 ai_chat.llm.timeout）
```

```text
⚠️ AI 对话出错（E-4c19）：PluginTimeoutError: 流式读取停滞 60s（上游不再吐数据，已生成 0 字正文）
（上游 60 秒没吐任何数据，已重试 2 次，像是它那边卡住了。再发一次通常就好；连续出现就把 ai_chat.llm.stall_timeout 调大）
```

> 文案由框架统一渲染：**群里会 @ 出错时提问的
> 那个人**，括号里是稳定错误编号 —— 用户报编号、`grep` 日志就能定位。
> 早先那句固定的 `error_prefix` 前缀已经退役（同一类失败在别处会以别的写法出现、
> 没有编号、也不 @ 人），现在全框架只有一套错误文案。

**为什么要单独写一版超时文案**：线上实测 `deepseek-v4-flash` 遇到「这段 C++ 会报什么
运行时错误」会**连想 200 秒以上**（流式观测：14 000 字思考链、正文 0 字；放开
`max_tokens` 到 16384 后网关自己 300 秒回 504）。而用户唯一能看到的就是
`TimeoutError` 四个字 —— 把「拆小问题 / 调大 timeout」写进提示，是他自己就能试的
第一步。判据是错误文本里是否含超时关键词，`401` 这类不沾边的失败**不会**被加上
这句（回归见 `test_llm_timeout_hint`）。

## 6.2 流式（默认开）：把「想得久」和「卡死」分开

**症状**：同一句「讲讲定积分，并列表分析定积分和不定分的差异」，有时 41 秒答完，
有时 3 分钟还没动静，用户重试三次全超时。

**根因**：非流式请求里，「模型正在想 100 秒」和「上游彻底卡死」长得**一模一样** ——
都是没有任何字节回来。于是只能定一个总超时一刀切：定小了（90s）把正常但慢的回答
砍掉，定大了（300s）真要卡死时又让用户白等。实测同一句话的耗时在 **78s～240s**
之间分布（思考链 1699～3670 字），90s 正好切在中间，成功率全看运气。

**改法**：请求改成 SSE 流式（`llm.stream`），判据随之换成两个：

| 判据 | 配置 | 语义 | 可重试 |
|---|---|---|---|
| **停滞** | `llm.stall_timeout`（默认 60s） | 这么久**没有新数据** → 判定卡死，掐断 | ✅ 是（多半是它那边抽了一下） |
| **总时长** | `llm.timeout`（默认 270s） | 单次调用的硬上限（防无限流） | ❌ 否（再试也是同样的时间） |

只要 token 还在流就一直等 —— 这正是流式带来的新能力。掐断时**已经生成的部分会
带在 `LlmError.partial` 里**，`_run_turn` 会把它发出去（前面加一句「以下是已经
生成的部分」），而不是让用户白等一场空。

其它行为：

- 上游不支持流式（忽略 `stream`、直接返回普通 JSON）时，自动退回非流式请求，
  不会因为端点不认流式就整条失败；
- `timeout` 之外还有一层更宽的硬上限兜底，避免任何情况下永久挂起；
- 掐断、超时、格式错误都会把**已经生成的部分**发给用户，并附一句说明。

## 空响应：思考吃光了配额

线上报过：

```text
⚠️ AI 对话出错（E-xxxx）：LlmError: 空响应（finish_reason=stop，思考链 181 字）
若为推理模型请调大 ai_chat.llm.max_tokens（建议 ≥ 16384）
```

原因：推理模型的**思考 token 与正文共用** `max_tokens`。当前 `max_tokens=4096`，
思考把配额用完 → 上游「正常结束」（`finish_reason=stop`）但 `content` 是空串。

现在**自动自愈**（`_chat_with_retry`）：

1. 第一次遇到 → 把 `max_tokens` 提到 `max(16384, 当前 × 4)` 重试一次；
2. 还空 → 用 `thinking:off` 再试一次（配额全留给正文）；
3. 两次都失败才把错误抛给用户。

所以正常情况下你**不会再看到**这个错误。如果它仍然出现，说明上游连着三次给了空正文，
那就是网关/模型的问题了 —— 日志里会有两行 `[ai_chat] 空响应（…），改用 … 重试一次`。
